# Changelog

User-facing changes, newest first. One entry per change that users can see.

## 0.4.0 — in progress

Lot 3, Full ticket lifecycle.

- Machines: each daemon package now has a **build**, a short code that changes whenever the daemon's program changes, so two daemons with the same version number are told apart. `orchestrator-daemon --version` and `orchestrator-daemon status` show it, and the machine's page shows its build next to the build this Orchestrator provides. When they differ, the machine still gets runs, but its page and "Needs you" say "The daemon on … is not the one this Orchestrator provides", with the commands to update it. Help: "Machines" > "Update the daemon".
- Machines: a 0.3.0 daemon connects to this Orchestrator but gets no runs, since it cannot do what this version needs: "Needs you" shows "Update the daemon on …", and the machine's page says why. Run now refuses the machine until it is updated.
- Machines: "Update the daemon on …" now gives the five commands that update a daemon installed as a service, with your Orchestrator's address filled in, ready to copy: stop the service, uninstall, install again from the Orchestrator (downloading it again even when the version number is the same), install the service, check the machine. Help: "Machines" > "Update the daemon".

- Runs: when an agent submits its work, its machine now pushes the ticket's branch to GitHub first, and only that branch: never another branch or a tag the agent made, and never by force, so a branch changed on GitHub meanwhile is left as it is and the push is reported as failed. Help: "Settings" > "Longest push".
- Settings > Limits: new **Longest push** (60 seconds), how long a machine lets one push take before stopping it; it also limits the download of the project when a run starts (the first download on a new machine is the longest). A run whose download is stopped fails, and its page now says why in the machine's words, naming the limit. Help: "Machines" > "Troubleshooting". The MCP call timeout plus Longest push must stay below the Claude Code MCP tool timeout; a value breaking this is refused, naming the three limits. Help: "Settings".
- Machines: the daemon now fetches from and pushes to GitHub in a separate place it prepares itself, never reading the Git settings of the project, of your user or of your computer, which an agent can change: a setting an agent added can no longer send your GitHub token to another computer or program (in 0.3.0, a proxy or a password program planted in the project's Git settings could receive it at the next fetch). A Git proxy set with `git config --global http.proxy` is no longer used: set `https_proxy` in the daemon's environment instead. Help: "Machines" > "Agents on your own user", which now also says what an agent could still do in this version and what a stolen token allows, and "Machines" > "Troubleshooting".

- Runs: when a run ends without a finished submission (the agent gave up, ran out of time or reminders, its session stopped, you clicked **Stop run** or cancelled the ticket), its machine now pushes the ticket's branch to GitHub when it holds commits GitHub does not have, once the agent's programs are stopped, so that work is not lost. This push never changes how the run ended; when it fails, the commits stay on the machine. Help: "Runs" > "Where the work is".
- Runs: when the ticket's branch changed on GitHub and contains the machine's commits (for example after **Update branch** on the pull request), the next run on that machine starts from GitHub's branch. A branch changed on GitHub in another way is left as it is. Help: "Runs" > "Where the work is".
- Runs: a push GitHub answers with "Repository not found" (the repository was deleted, or the token cannot see it) is now reported as refused by GitHub, not as GitHub unreachable.
- Machines: when the last run of a project on a machine ends, the machine puts back the project's Git settings and hooks it shares between runs, as the Orchestrator wrote them, and Activity shows "Git configuration restored", naming what it found changed by an agent or one of its tools, in that run or an earlier one (never the values). While another run of the project is still on the machine, nothing is put back. Information only. Help: "Machines" > "Agents on your own user".
- Agents: the Architect and the Web Developer may bring the project's latest changes into their branch with `git merge origin/main`, and undo it with `git merge --abort`; they never rebase. Their versions go up by one. Help: "Agents".

## 0.3.0 — 2026-10-03

Lot 2, Machines and manual runs: add your Claude accounts and machines, start an agent on a ticket with **Run now**, watch it work live, answer its questions, accept or reject the tickets it proposes, and check its finished work and its commits on the ticket's branch. The scheduler, pull requests and CI come in the next versions.

- Machines: `orchestrator-daemon login` can be typed in any folder: Claude Code opens in an empty folder of the Orchestrator's own, so it no longer asks whether you trust the terminal's folder, nor reads that folder's files. Help: "Machines" > "Add a machine" says what to answer.
- Machines: Claude Code 2.1.287 is now the latest version checked with this Orchestrator: no warning on a machine with it.
- Runs: the run's log no longer says "N transcript line(s) could not be read and were skipped" for the lines Claude Code 2.1.287 adds, none of which holds the agent's work; the warning stays for lines really unknown.
- Agents: each agent is now told the list of commands it may run, and that any other is refused. When a ticket really needs a command it may not run, the agent says so in plain words and asks you how to go on, or gives up the ticket. Help: "Agents".
- Help: "Machines" > "Add a machine" points to "Runs" > "Try it with a small ticket", which now gives its two acceptance criteria one per line.
- Machines: `orchestrator-daemon status` with no daemon running says how to start it once, instead of twice after the service was stopped.
- Agents: every agent now changes files with its editing tools, runs one command at a time, and when a command is refused, runs its allowed parts on their own before asking you; it asks you only what you can decide, never to allow a command. Before, an agent whose chained command was refused asked to "allow Bash for git add and git commit". Help: "Agents".
- Machines: agents can no longer run the container tools `docker`, `docker-compose`, `podman`, `nerdctl` and `kubectl`: your user can use them, and the Orchestrator may run in Docker on the same computer, where a container's configuration could show its secret key. Before, Claude Code let `docker ps` through by itself. Help: "Machines" > "Agents on your own user".
- Machines: `orchestrator-daemon install-service` turns lingering on with your user name, which works on WSL without `sudo` (it failed with "No such device or address" before); when it still fails, it shows loginctl's own reason and the command to type, as `orchestrator-daemon doctor` does. Help: "Machines" > "Lingering".
- Settings > Limits: the limits used from this version on no longer say "it changes nothing in this version"; the note stays only on limits of later versions, and Help > Settings says which project limit already changes something.
- Machines: stopping or restarting the daemon (`systemctl --user restart orchestrator-daemon`) no longer waits up to 30 seconds when the Orchestrator does not answer: it stops as soon as its own work is done.
- Machines: the daemon's service now checks that it can create the process scopes that keep agents' sessions running when the service restarts. Before, it went on without them and the next restart stopped every agent's session. When it cannot create them, the machine stays online but takes no runs, and "Needs you" shows the problem with the reason and how to fix it; `orchestrator-daemon status` and `orchestrator-daemon doctor` show it too. If a run's scope cannot be created later, that run fails without counting as a failed attempt (its ticket goes back to To do), and the machine takes no runs until the daemon is restarted. Help: "Machines" > "Process scopes".
- Help: "Runs" > "Try it with a small ticket" gives a tiny ticket to try the Orchestrator or a new machine with little of your Claude usage, including a question to answer and a ticket the agent proposes.
- Machines: when a run's session closes, the daemon now waits until every program it left has exited before it removes the run's folders or lets a resumed run use them again; a program that kept starting new ones could leave one running before.
- Server: `orchestrator reset-password` prints its "could not be changed" message instead of stopping with an error when PostgreSQL restarts while it runs.
- Machines: the daemon no longer stops when it cannot write a run's files (a full disk, a removed folder): it logs the error, the run goes on, and the files are written again a second later. Stopping the daemon now waits for what its runs are doing, so nothing is left half done.
- Needs you: lists what agents' work leaves for you, oldest first: their questions, answered right there; the tickets they propose, with **Accept** and **Reject**; finished work to check (In review), with the agent's summary, **Mark as done manually** and **Request changes**; and runs paused by a usage limit, with **Resume** and **Stop run**. A line per Claude account says whether it is available or limited until when. Help: "Needs you".
- Tickets: **Request changes** on a ticket In review sends it back to To do with your comment (required); the branch and commits are kept, it does not count as a failed attempt, and the next dialog offers **Run now**. The next run continues the earlier commits and reads your comment. Help: "Tickets" > "Request changes" and "Runs" > "Check finished work".
- Runs: a run paused on a Claude usage limit says when you can resume it, with "(estimated)" when Claude gave no reset time; **Resume** becomes available by itself at that time. A run paused on a possible limit says it may pause again if it was the limit. Help: "Runs" > "Usage limits".
- Activity: **Live runs** shows every run in progress with what its agent does now (its latest log entry, updated as it works), **Stop run** and the command to watch it in a terminal; **History** lists ended runs with filters by project, agent, outcome and dates, and says why a failed run failed. Help: "Activity".
- Machines: each Claude account shows its state (available, or limited until when), and the machine list and page show the runs in progress on each machine. **Add machine** warns when machines would reach the Orchestrator over plain `http://` from another computer, which the daemon refuses. Help: "Machines".
- Machines: `orchestrator-daemon status` lists the ticket branches kept on the machine with their commits not on GitHub yet, and which run uses each; it works even when the daemon is stopped, and changes nothing. Help: "Machines" and "Runs" > "Where the work is".
- Runs: **Run now** on a ticket in To do starts its agent on one of your machines and opens the run page, or says in plain words why it cannot start. The run page shows the run's status, the time spent working and waiting, the estimated usage, the agent's progress line and its log as it happens. **Stop run** stops it (the ticket goes back to To do and the branch is kept) and **Resume** continues a run paused on a Claude usage limit. The ticket page shows the run in progress, every run of the ticket, the failed attempts, the agent's report, and the branch "on machine …, not on GitHub yet" with its commits. Help: new "Runs" page.
- Questions: an agent's question appears on the ticket page and the run page, with a box to answer it. Help: "Runs" > "Questions".
- Tickets: the board has a **Proposed** column while an agent has proposed a ticket, cards show "created by agent" and the run in progress with its latest progress line, and a proposed ticket has **Accept** and **Reject** (with an optional comment). Help: "Tickets" > "Tickets proposed by agents".
- Every screen now updates by itself as things change, without reloading, and catches up after a lost connection. The project page no longer checks its repository setup every few seconds, and the **Setup progress refresh** limit is removed from Settings > Limits (a value you had set is dropped).
- Agents can now talk to the Orchestrator during a run: read the project, tickets and comments, show a progress line, add notes, ask you a question, propose new tickets and submit or give up their ticket. A submitted ticket moves to In review with the agent's report. A question makes the ticket wait for you; your answer reaches the agent at once, even after its session was closed (it then resumes on the same machine), and if that machine is offline the run ends without counting as a failed attempt and the next run reads your answer. Tickets an agent proposes wait for you to **Accept** or **Reject** them. The screens for all this came in a later step of this version (see above).
- Settings > Limits, Runs: new **Progress update interval** (60 seconds), the shortest time between two progress lines shown for a run; the agent's updates are never refused. Used from version 0.3.0. Help: "Settings".
- Activity: the event log shows what agents change (their notes, questions, proposed tickets, submissions and new progress lines), marked with the actor "Agent", and your answers, **Accept** and **Reject**. Agents reading tickets write nothing there.
- Machines: restarting the daemon's service (`systemctl --user restart orchestrator-daemon`) no longer ends the agents' sessions: they keep running and the daemon finds them again. When a run's session closes, every program it left running (even one started with `nohup` or `setsid`) is stopped, so nothing keeps working in a removed folder. Help: "Machines".
- Runs on the server: the Orchestrator can start a run of the ticket's agent on one of your machines, follow it, stop it, pause it on a Claude usage limit and resume it. The buttons and the run screens came in a later step of this version (see above). Cancelling a ticket or marking it as done stops its run.
- Needs you: "… is offline with work on it" lists a machine that went offline while agents' runs were on it. "Claude Code not supported" also appears when a run finds Claude Code too old as it starts; that run does not count as a failed attempt. Help: "Needs you".
- Settings > Limits: **Most acceptance criteria** times **Longest acceptance criterion** is at most 20,000 characters, so every ticket's criteria fit in an agent's first message; a value going above it is refused, naming both limits, their values and the 20,000 characters. New **Longest stored log entry** (2,000 characters) in Runs. **Quota wait when the reset time is unknown** is used from version 0.3.0. Help: "Settings".
- Activity: the event log shows runs (started, each change of status and why), the ticket moves they cause, Claude accounts reaching their usage limit and becoming available again, and a machine whose Claude Code is too old at a run's start.
- Agents: the Web Developer no longer tries to open the project in a browser, which it does not have, and never starts a dev server or another long-running or background process; it checks its work with the project's tests, end-to-end tests and build. An agent's first message says which attempt at the ticket this is and, when earlier work is on the ticket's branch, tells the agent to continue it.
- Tickets: choose the **Assignee**, the agent expected to do the work (**Architect** or **Web Developer**), when you create or edit a ticket in To do. Cards and the ticket page show it, and the board filters by assignee, including **Unassigned**. Help: "Tickets" > "Assignee".
- Help: a new "Agents" page describes the Architect and the Web Developer, the rules every agent follows, and the commands each may run. "Machines" > "Agents on your own user" explains that this list does not protect your computer, and that web pages an agent reads could hide instructions.
- Activity: the event log shows the agents added or updated with a new version of the Orchestrator, and the assignee of tickets.
- Help: "Machines" > "Agents on your own user" says that Claude Code shows every agent your Claude account's e-mail address and your Git user name and e-mail address.
- Machines: agents are kept out of the Orchestrator's folder, the Claude configuration folders, your home folder and everything outside the project; they cannot run Git commands that reach GitHub or another computer (which could use your own GitHub login, as Git Credential Manager keeps it on WSL), `gh`, or `tmux`. Each refusal tells the agent why. Help: "Machines" > "Agents on your own user".
- Settings > Limits, Runs: new **MCP call timeout** (30 seconds), how long a machine waits for the Orchestrator's answer to an agent's tool call, and **Claude Code MCP tool timeout** (120 seconds), always above it: a value breaking this is refused, naming both limits and their values. Both are used from version 0.3.0. Help: "Settings".
- Settings > Limits, Runs: new **Session start timeout** (30 seconds), how long a machine waits for Claude Code to start a run's session. **Idle timeout** now stops a run whose agent shows no activity, without a reminder; time running a command does not count. Both are used from version 0.3.0. Help: "Settings".
- Activity: the event log also hides machine keys (`omt_…`) if one ever appears in a comment or a change.
- Help: "Machines" > "Agents on your own user" explains that an agent could send false news about its own run, and that it can never touch another ticket or project.
- Settings > Limits has a Machines group: **Enrollment code lifetime** (15 minutes), **Heartbeat interval** (15 seconds) and **Machine offline after** (60 seconds, at least twice the heartbeat interval: a value breaking this is refused, naming both limits and their values). Help: "Settings".
- Activity: the event log shows what happens to Claude accounts and machines (added, enrolled, connected, offline, disabled, revoked, capabilities edited), in plain words, with a filter for each.
- Machines: add your Claude accounts (label, plan, runs at the same time) and the computers where agents will work. **Add machine** shows the commands to type on the computer (install the daemon from the Orchestrator, enroll with a one-time code, log in to Claude, start the service) and shows when it connects. Each machine's page shows its status, versions (with a warning for a Claude Code newer than the one checked), the daemon's checks, and lets you edit its capabilities, disable, enable or revoke it, and get a new enrollment code. Help: "Machines", including how to keep WSL running.
- The machine daemon: `orchestrator-daemon` installs from the Orchestrator with the command shown on **Add machine**, then `enroll` (with `--ca-file` for an Orchestrator using its own certificate authority), `login`, `install-service` (the service, with the tools of your terminal), `start`, `status` and `doctor`. The daemon reconnects by itself after a network problem or a restart of the Orchestrator, and stops with a message saying what to do when it was revoked, is outdated, or another daemon uses its key. A plain `http://` address is accepted only for an Orchestrator on the same computer: machines on other computers need HTTPS. Help: "Machines", including "Orchestrator on another computer" and Troubleshooting.
- Needs you: shows "No Claude account yet" and "No machine enrolled yet" until you add them, and machines that cannot work (daemon to update, Claude Code missing or too old, a problem found by the daemon's checks), each with the commands to fix it. Help: "Needs you", "Machines".
- The Orchestrator keeps running when its database restarts, even during a change in progress: it notes the lost connection in its log and uses a new one; only that change fails, and can be made again.

## 0.2.0 — 2026-09-24

Lot 1, Projects and tickets: create projects with a new or linked GitHub repository, manage their tickets, change the limits and read the event log. Agents, machines and runs come in the next versions.

- Activity: the event log lists everything that changed, newest first, in plain words, with links to the project or ticket, and filters by project, ticket, kind, event and days. Quoted titles, names and comments are shortened plain text linking to the full text; credentials are never shown. The project list shows each project's last activity (time of its latest event, opening its event log) instead of "Last change". Help: "Activity".
- Settings > Limits: change the limits and timeouts of the Orchestrator (login and sessions, GitHub, tickets, and those of later versions, marked "Used from version ..."), each with its default and **Reset to default**. A change applies at once, without a restart, and is recorded. Project settings show the limits a project can override. Nothing changes for you until you change a value: every limit keeps the value it had. Help: "Settings".
- Tickets: each project page has a board of its tickets, by state (on a phone, the states are one below the other), with filters by type and text and a "Blocked" badge. Create and edit tickets (type, title, description, ordered acceptance criteria, priority, dependencies), comment on them, cancel, mark as done manually (with a required comment) and reopen them. The ticket page lists the tickets it waits for and the ones waiting for it, and says what to do when it waits for a cancelled ticket. The project list shows the number of tickets in each state. Descriptions and comments use Markdown, shown safely: no HTML, only web and e-mail links, images as links. Help: "Tickets".
- Tickets: **Mark as done manually** warns when the ticket still waits for tickets that are not done, naming them with their states, and asks you to confirm with **Mark as done anyway**. Help: "Tickets", "Mark as done manually".
- Every refusal is explained in plain words, and a text that is too long names the field and its limit.
- Projects: create a project with a new GitHub repository (private by default) or link one of your repositories, follow its setup on the project page, try a failed setup again, change its name and description, archive and unarchive it (the GitHub repository is never changed). A linked repository shows the harness elements it is missing, with **Check again**. "Needs you" lists projects whose setup failed. Help: "Projects".

## 0.1.0 — 2026-09-23

First version (lot 0, Foundations): install the Orchestrator with Docker Compose, create your account, connect GitHub and read the user guide in the Help section. Projects, machines and agents come in the next versions.

- The GitHub token check no longer reports Workflows as Missing when only Contents is missing: Workflows then shows "Could not verify" with "Requires Contents (Read and write) first", since GitHub cannot check Workflows without Contents.
- The Orchestrator has screens: open `http://localhost:8080`. A setup wizard creates your account and connects GitHub, with a "Create the token on GitHub" button that fills in GitHub's token form for you; then you log in with your username and password.
- "Needs you", the home page, warns you when the GitHub token expires within 14 days, has expired, is refused by GitHub or misses a permission. Settings > GitHub connection shows the token's account, expiry date and permissions, checks it again and replaces it.
- The Help section shows the user guide, with a search box, starting with "Getting started". Every screen links to its Help page.
- Every screen works on a phone: the menu is behind the "Menu" button.

- After several failed logins, the Orchestrator makes you wait before trying again, longer after each new mistake.
- If the secret key in `.env` is lost or changed, the Orchestrator keeps running and asks you to enter your GitHub token again (Help: "Back up your secret key").

- A forgotten password can be reset with `docker compose -f docker/compose.yml exec orchestrator orchestrator reset-password` (see the Help page "Reset a forgotten password"). The account and GitHub screens arrive in the next version.

- The Orchestrator starts with Docker Compose (`docker compose -f docker/compose.yml up --build`): the server and its database, with a health check. There is no screen yet.
