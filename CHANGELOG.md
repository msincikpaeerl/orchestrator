# Changelog

User-facing changes, newest first. One entry per change that users can see.

## 0.4.0 — in progress

Lot 3, Full ticket lifecycle.

- Machines: each daemon package now has a **build**, a short code that changes whenever the daemon's program changes, so two daemons with the same version number are told apart. `orchestrator-daemon --version` and `orchestrator-daemon status` show it, and the machine's page shows its build next to the build this Orchestrator provides. When they differ, the machine still gets runs, but its page and "Needs you" say "The daemon on … is not the one this Orchestrator provides", with the commands to update it. Help: "Machines" > "Update the daemon".
- Machines: a 0.3.0 daemon connects to this Orchestrator but gets no runs, since it cannot do what this version needs: "Needs you" shows "Update the daemon on …", and the machine's page says why. Run now refuses the machine until it is updated.
- Machines: "Update the daemon on …" now gives the five commands that update a daemon installed as a service, with your Orchestrator's address filled in, ready to copy: stop the service, uninstall, install again from the Orchestrator (downloading it again even when the version number is the same), install the service, check the machine. Help: "Machines" > "Update the daemon".

- Runs: when an agent submits its work, its machine now pushes the ticket's branch to GitHub first, and only that branch: never another branch or a tag the agent made, and never by force, so a branch changed on GitHub meanwhile is left as it is and the push is reported as failed. Help: "Settings" > "Longest push".
- Settings > Limits: new **Longest push** (60 seconds), how long a machine lets one push take before stopping it; it also limits the download of the project when a run starts (the first download on a new machine is the longest). A run whose download is stopped fails, and its page now says why in the machine's words, naming the limit. Help: "Machines" > "Troubleshooting". The MCP call timeout plus Longest push must stay below the Claude Code MCP tool timeout; a value breaking this is refused, naming the three limits. Help: "Settings".
- Machines: the daemon now fetches from and pushes to GitHub in a separate place it prepares itself, never reading the Git settings of the project, of your user or of your computer, which an agent can change: a setting an agent added can no longer send your GitHub token to another computer or program (in 0.3.0, a proxy or a password program planted in the project's Git settings could receive it at the next fetch). A Git proxy set with `git config --global http.proxy` is no longer used: set `https_proxy` in the daemon's environment instead. Help: "Machines" > "Agents on your own user", which now also says what an agent could still do in this version and what a stolen token allows, and "Machines" > "Troubleshooting".

- Runs: when a run ends without a finished submission (the agent gave up, ran out of time or reminders, its session stopped, you clicked **Stop run** or cancelled the ticket), its machine now pushes the ticket's branch to GitHub when it holds commits GitHub does not have, once the agent's programs are stopped, so that work is not lost. This push never changes how the run ended; when it fails, the commits stay on the machine. Help: "Runs" > "Where the work is".
- Runs: when the ticket's branch changed on GitHub and contains the machine's commits (for example after **Update branch** on the pull request), the next run on that machine starts from GitHub's branch. A branch changed on GitHub in another way is left as it is. Help: "Runs" > "Where the work is".
- Runs: a push GitHub answers with "Repository not found" (the repository was deleted, or the token cannot see it) is now reported as refused by GitHub, not as GitHub unreachable.
- Machines: when the last run of a project on a machine ends, the machine puts back the project's Git settings and hooks it shares between runs, as the Orchestrator wrote them, and Activity shows "Git configuration restored", naming what it found changed by an agent or one of its tools, in that run or an earlier one (never the values). While another run of the project is still on the machine, nothing is put back. Information only. Help: "Machines" > "Agents on your own user".
- Agents: the Architect and the Web Developer may bring the project's latest changes into their branch with `git merge origin/main`, and undo it with `git merge --abort`; they never rebase. Their versions go up by one. Help: "Agents".
- Tickets: the **Branch** part of the ticket page now says where the commits are: only on a machine, on GitHub (pushed by the Orchestrator, or brought by GitHub itself, such as **Update branch**; with the date and machine of the last push, and a link to the branch on GitHub), or both, with the commits not on GitHub listed apart. A review never changes where the work is. When a push failed, it says when and why, including when GitHub's branch has commits the machine does not have. "Pushed" is what the Orchestrator pushed, not a reading of GitHub: a change made on GitHub is not shown in this version. Tickets started with 0.3.0 read as before. Help: "Runs" > "Where the work is".
- Runs: once every commit of a ticket's branch is pushed, **Run now** can start the next run on any machine, which downloads the branch from GitHub; only commits not on GitHub tie a ticket to the machine holding them. When **Run now** refuses for that reason, it says how many commits are not on GitHub. A revoked machine now loses only its commits not on GitHub, and the next run starts from the branch as last pushed. Help: "Runs" > "Where the work is".
- Runs: the run page shows what the run pushed to GitHub, or why its push failed; the comment of a failed attempt says "Every commit of the branch … was on GitHub when the run ended" when it was. Activity shows "Branch pushed to GitHub" and "Branch push failed".
- Runs: when the machine cannot push the branch as the agent submits its work (GitHub refused it, the branch changed on GitHub, or GitHub could not be reached), the run ends at once with "its branch could not be pushed to GitHub", which does not count as a failed attempt; the agent cannot fix it, so it spends no more time trying. Help: "Runs".
- Needs you: when the work could not be pushed to GitHub as the agent submitted it, an item says what happened and what to do: the token permission to give, in the words of GitHub's token page ("Contents (Read and write)", or "Workflows (Read and write)" when the work changes a GitHub workflow), with a link to your tokens on GitHub; GitHub's own words for any other refusal; the branch changed on GitHub; or GitHub could not be reached. **Run now** on the ticket then continues on the machine holding the work, and the item goes as soon as a push of the branch succeeds. The ticket gets a comment saying the same. Help: "Tickets" > "When the work cannot be pushed to GitHub".
- Runs: when the ticket's branch changed on GitHub so that the machine's push was refused, the next run first brings GitHub's commits in with a merge, then continues and pushes. Help: "Tickets" > "When the work cannot be pushed to GitHub".
- Runs: an agent's submission is now checked further: a docs ticket must list a documentation file its branch changed (a README.md counts), a spike an ADR or a document, and every file the report lists must be a file the branch changed (folders are not accepted). When a machine could not send the whole list of changed files, the check says it could not be fully done and never refuses the work. Each check's result is kept, for the work accepted and for the latest refused submission of each run. Activity shows "Submission refused by the checks", naming the failed checks.
- Agents: the Architect's and the Web Developer's instructions now say how a submission is checked and what to do when the push fails or the branch changed on GitHub. Their versions go up by one. Help: "Agents".
- Fixed: a change made while a page was loading (a run's CI check, for example) could stay off the screen until the next change. Every page now reads its data again once the live updates connect.
- Fixed: a run stopped while its machine was still preparing it (downloading the project, making its folder) no longer starts its Claude Code session afterwards; the same holds for a waiting or paused run stopped while its session starts again.
- Settings > GitHub: the permissions check now also checks that the token can read pull requests, on one of your private repositories; Pull requests shows **OK** only when reading and writing both are. Without a private repository, it shows **Could not verify**. Help: "Connect GitHub" > "The permissions check".
- Agents: a third agent, **Quality**, reviews the work other agents submit: it reads the changes and runs the project's tests and build, but never edits a file, commits or moves the branch. It cannot be chosen as a ticket's assignee: the ticket form no longer offers it, and choosing it is refused. Help: "Agents" > "Quality".
- Tickets: when an agent's work passes the checks, the Orchestrator now opens the ticket's pull request on GitHub just after answering the agent, or updates it at a later submission; one closed without merging is reopened, and a new one is opened when the last was merged. Its title is the ticket's number and title, its description the agent's report and a link to the ticket. Nothing in it can notify anyone, close an issue or show HTML, secrets are hidden, and long texts are cut within GitHub's limits. Activity shows "Pull request opened", "reopened", "updated" and "not opened". Help: "Tickets" > "The pull request".
- Needs you: "Pull request not opened for …" when GitHub could not open or update it, saying why (the token permission in the words of GitHub's token page, "Pull requests (Read and write)"; GitHub unreachable; the token; GitHub's request limit; an answer this version cannot read, with what differed; or GitHub's own words), with **Try again**. The Orchestrator also tries again each time it starts and while the run waits for CI, and never opens a second pull request. The item's "Since" is the first failed try, and Activity shows one event when tries start failing or fail for another reason, not one per try. Help: "Needs you" > "Pull request not opened".
- Tickets: the ticket page shows the pull request, "Pull request #12 · Open" with its link to GitHub (the state the Orchestrator saw when it last opened or updated it), "Opening the pull request on GitHub…" just after the work is accepted, and "Pull request not opened: <reason>" with what to do and **Try again**. Help: "Tickets" > "Submission and the pull request".
- Tickets: the **Agent's report** now lists the tests, documentation and architecture decisions the agent gave, and **Checks**: each check of the accepted work with "Passed" or "Could not be fully done", and why in plain words; the agent's own message is folded under "What the agent was told". Long lists show 10 lines and fold the rest. Work accepted by 0.3.0 says it was checked by an earlier version. Help: "Tickets" > "The checks".
- Tickets: a warning when the work changes GitHub workflow files ("Workflow files changed"), or when the machine could not send the whole list of changed files ("Workflow files may have changed"), saying to look at the changed files on the pull request before merging. Help: "Tickets" > "Workflow files".
- Runs: the run page shows the **Latest refused submission**: when the checks refused the agent's work, each check's result and why in plain words, so you see what an agent keeps getting wrong; when the work was accepted afterwards, the card says so with its date. Help: "Runs" > "Watch a run".
- Tickets, Needs you and Activity: when the ticket's pull request is open and a later accepted submission could not update it, they say "Pull request not updated" (its description still shows the earlier submission's report; the new commits are on GitHub, in the pull request) instead of "not opened". Help: "Tickets" > "The pull request", "Needs you" > "Pull request not opened".
- Runs: an accepted submission now waits for CI on GitHub before the ticket moves to **In review**. The run page says "waiting for CI"; the agent's session stays open and idle, using none of your Claude usage, and its time counts as waiting. Only the commit the machine pushed counts, never an older one of the branch. CI passed, or nothing appeared within the new **Wait for CI to start**: the run ends as succeeded. A pull request that conflicts with the default branch, which GitHub runs no CI on, is never accepted. A failed CI or a conflict goes back to the agent in the same session (see below). Still running at **CI wait at submission**: the run ends without counting as a failed attempt. GitHub unreachable, its request limit or an answer that cannot be read never end the wait, and a restart of the Orchestrator or of the agent's session loses nothing. Activity shows "Waiting for CI", "CI result", "CI could not be checked on GitHub" and "CI checked on GitHub again". Help: "Tickets" > "Waiting for CI".
- Settings > Limits: new **GitHub check interval** (60 seconds), how often the Orchestrator asks GitHub about a submission waiting for CI, and **Wait for CI to start** (5 minutes, per project), after which a submission with no CI passes as "No CI found". Help: "Settings".
- Agents: the instructions say to end the turn once a submission is accepted, while CI runs. Every default profile's version goes up by one.
- Runs: while a run waits for CI, its status reads **Waiting for CI** (run page, Activity, board), and the run page shows a **CI** card: the commit and pull request, since when and until when it waits, when GitHub was last checked, the pull request not opened yet, nothing appeared yet (and by when it passes as "No CI found"), a conflict with the default branch, a line when GitHub could not be checked (since when and why, with the time GitHub allows requests again), and each workflow run and status with **Not finished**, **Passed** or **Failed**. Help: "Runs" > "Waiting for CI".
- Agents: the `ci_status` tool now answers with the CI result of the ticket's latest accepted work, naming its commit, which run handed it in, and when it was read on GitHub; for a failure, each failed job with the part of the log of each failed step, secrets hidden. It asks GitHub at most once per **GitHub check interval** and never again for a finished result, so an agent calling it again and again does not use up GitHub's request limit. Help: "Runs" > "Waiting for CI".
- Settings > Limits: new **Longest CI log excerpt** (4,000 characters), how much of each failed CI step's log an agent receives, and **Longest CI log read** (20 megabytes), how much of a failed job's log is downloaded from GitHub to find each step's part. Help: "Settings".
- Runs: when CI fails, the agent now gets the failure back in the same session, each failed job and step with its part of the log (secrets hidden), fixes its work and hands it in again, checked from the start; handing in the same commit again is refused. When the pull request conflicts with the default branch, the machine downloads that branch first and the agent is told to merge it and resolve the conflict. Each result sent back is a CI round and counts within the new **Most CI failures per run** (2, per project) once the machine confirmed it received it; one more ends the run as a failed attempt, and the next run's agent is told to read that result first. Runs GitHub cancelled because the branch changed there end the run at once without counting, and the next run starts from GitHub's branch. Activity shows "CI result sent to the agent" and "CI result not taken by the machine". Help: "Tickets" > "Waiting for CI".
- Tickets: **Check CI again** reads CI on GitHub for the work handed in, without starting a session, after **CI wait at submission** was reached or after one CI failure too many: when CI has passed since, the work is accepted and the ticket moves to **In review**, and a failed attempt for that commit no longer counts. It is also the way to read CI again after you re-ran a workflow by hand on GitHub. It says what it found otherwise (still running, failed, a conflict, GitHub not reachable), and why it is refused (a run working, newer work, the branch changed on GitHub, the pull request closed, merged or not opened yet). Activity shows "CI checked again". Help: "Tickets" > "Check CI again".
- Tickets: the ticket page shows a CI line under the pull request: waiting, passed, "No CI found", failed after too many failures (or failures or conflicts), not finished, failed without the agent getting the result, a conflict, cancelled because the branch changed, or a run that ended after a round; each says what to do. Help: "Tickets" > "The CI line".
- Runs: the run page's **CI** card lists each CI round of the run (sent back to the agent, not confirmed by the machine, or not sent back), the result that ended the run, and the work accepted later by **Check CI again**, each with its checks. A run that reached **CI wait at submission** now says what was found in its comment, never that CI did not finish when it had failed. Help: "Runs" > "Waiting for CI".
- Needs you: a run that reached **CI wait at submission** leaves "CI did not finish for …" with **Check CI again**, "CI failed for …, and the agent did not get the result" or "… conflicts with main", both with **Run now**. Help: "Needs you" > "CI items".
- Settings: **CI wait at submission** and **Most CI failures per run** are explained in new words. Help: "Settings".
- Help: "Connect GitHub" says what each token permission does from 0.4.0, names them as "Needs you" does ("Contents (Read and write)", "Workflows (Read and write)", "Pull requests (Read and write)"), and links to GitHub's page on GitHub Actions minutes for private repositories. "Tickets" > "Ticket states" no longer says the work In review is only on your machine.
- Reviews: a ticket whose work was accepted and whose CI passed (or found nothing to run) is now **Ready for review** in "Needs you" and on the ticket page, with its pull request, the CI result, a line when the work changed workflow files, and what each choice costs. **Start review** asks Quality to review the commit CI checked, in one Claude Code session; **Skip review** (after a confirmation) moves the ticket to **Awaiting merge** without a session. "Work finished: check it" stays only for tickets left in review by 0.3.0 without a pull request. Help: "Tickets" > "Review by Quality".
- Reviews: Quality approves the work (the ticket moves to **Awaiting merge**) or asks for changes (each point becomes a comment and the ticket goes back to **To do**; it never counts as a failed attempt). It may ask you a question, as other agents do. When CI passed it does not run the tests again unless it has a reason; when no CI ran, it runs them itself. It never reviews a ticket it implemented. Help: "Tickets" > "Review by Quality", "Agents" > "Quality".
- Reviews: each review is also posted on the pull request as a comment review (GitHub refuses approvals and change requests on your own pull request), made harmless like the pull request's description: no notifications, no closed issues, secrets hidden. The ticket page shows **Posted on GitHub** with its link, or a note saying why it is not known to be there; the decision stands either way. Activity shows "Quality's review posted on GitHub" and "Quality's review not known on GitHub", and "Quality's decision recorded" and "not applied". Help: "Tickets" > "The review on GitHub".
- Reviews: a review is about one commit. When the pull request changed on GitHub (before or during the review) or the branch changed on the machine, the review does not apply. A review run that ends without a decision applied (Quality gave up, its time ran out, its machine went offline, you stopped it, the work changed) leaves the ticket in review, never counts as a failed attempt, and "Needs you" shows "Review did not finish" saying why, or which decision Quality had made and why it was not applied, with **Start review** and **Skip review**. Help: "Tickets" > "When the review did not finish".
- Tickets: the ticket page's **Review** shows the latest review ("Approved by Quality" with its summary, "Changes requested by Quality" with each point, "Review skipped by you", "Review in progress"), and says so when it is about an earlier submission than the work now in review. A ticket in **Awaiting merge** says to merge its pull request on GitHub, then use **Mark as done manually**, since this version does not notice the merge yet. **Request changes** is not offered while Quality is reviewing. Help: "Tickets" > "Ticket states".
- Runs: the run page of a review shows its review card: the commit reviewed and its pull request, the decision (or none), why a decision was not applied, and the review's post on GitHub. Help: "Tickets" > "Review by Quality".
- Agents: Quality now follows rules of its own instead of the rules of the agents that do the work: it ends a review by approving, asking for changes, asking you or giving up, and is no longer told to submit, commit, merge or edit files; it changes no file itself (what installing, building and testing leave behind is expected), and puts what it finds into its approval or its points, not into separate notes. The Architect's and the Web Developer's rules are unchanged, apart from two sentences about reviews. Every agent's version goes up by one. Help: "Agents" > "What every agent follows".
- Reviews: after a request for changes, Quality's or yours, **Run now** starts a **Fix after review** run: the agent gets the points first (or your comment), continues on the same branch and pull request, explains in a comment any point it leaves, and hands in a new commit, which goes through CI and back to **In review**. Handing in the same commit again is refused ("Same commit as the one Quality asked changes on"). The ticket page in **To do** says "Run now starts a run that addresses Quality's points (round 1 of at most 2)." or "… your request.". The next review is told of the earlier points and of the agent's answers, then reviews the whole work. A failing fix run counts as a failed attempt; Quality's request never does. Help: "Tickets" > "The round after a request".
- Reviews: the new setting **Most review rounds per ticket** (2 by default, also per project). When Quality asks for changes once more than it allows, the request is applied, then the ticket stops: **Stopped** on the board and the ticket page, "Stopped after too many review rounds" in "Needs you", and **Run now** refused. **Try again** (no session) counts the review rounds and failed attempts from 0 again and offers **Run now** at once; **Cancel the ticket** and **Mark as done manually** are next to it. **Reopen** also counts the rounds from 0. Help: "Tickets" > "Too many review rounds".
- Reviews: **Request changes** is now offered on **Awaiting merge** too, after Quality's approval or your **Skip review**: nothing is posted on GitHub, the pull request stays open, and the ticket page keeps the approval with "You requested changes after this approval, at …" until the fix is in review. When you disagree with Quality's request, merge the pull request on GitHub and use **Mark as done manually**, also from **To do** or from a stopped ticket. Help: "Tickets" > "Request changes after an approval" and "When you disagree with Quality".
- Reviews: **Start review** is no longer refused when the earlier review's points, your request, the agent's comments about them or the earlier reviews are too long for Quality's first message: the oldest parts are left out first, each with a note telling Quality how to read them.
- Tickets: a ticket whose pull request you merge on GitHub now moves to **Done** by itself, whatever merge method you use (merge commit, squash or rebase), at the Orchestrator's next check of GitHub (every **GitHub check interval**, in Settings > Limits). A run still working on it is stopped, without counting as a failed attempt; tickets waiting for it are unblocked and its items leave Needs you. A comment says when GitHub merged it, its latest commit then, what CI said of that commit and Quality's review. A ticket you marked as done manually first only gets a comment; a cancelled ticket stays cancelled, with a comment; a pull request merged into another branch than the default one changes nothing. Help: "Tickets" > "Merging the pull request".
- Tickets: the pull request's state on the ticket page (**Open**, **Closed without merging**, **Merged**) is now read again at every GitHub check, and a pull request you closed without merging stays watched while the ticket is open, so reopening (and merging) it on GitHub is seen. Activity shows "Pull request merged" and "Pull request closed without merging".
- Runs: when the pull request's latest commit on GitHub is exactly the latest commit a machine reported, that machine's commits count as on GitHub, so **Run now** can take any machine. Help: "Runs" > "Where the work is".
- Tickets: once a ticket's pull request is merged into the default branch, the Orchestrator deletes the ticket's branch on GitHub, after any run the merge stopped has reported its end (its last push included). It keeps the branch, and says why, when another open pull request uses it, when commits were pushed to it after the merge, when the pull request was merged elsewhere or came from a fork, or when GitHub refuses. A branch already deleted on GitHub counts as deleted; nothing is deleted after a cancellation. It uses the token's **Contents (Read and write)**. Activity shows "Ticket branch deleted on GitHub", "Ticket branch kept on GitHub" and "Ticket branch on GitHub again".
- Machines: after the merge, each machine where a run worked on the ticket deletes its copy of the ticket's branch, only when that copy's latest commit is the merged one; otherwise it keeps it, since it may hold work that was not merged. An offline machine is asked when it reconnects, a busy one at the next check, and one with an older daemon once its daemon is updated. Activity shows "Ticket branch deleted on a machine" and "Ticket branch kept on a machine".
- Tickets: the ticket page's new **Clean-up after the merge** section shows the ticket's branch on GitHub and on each machine, with its real name: deleted, already gone, kept with the reason, or what it waits for (a run's end, an offline machine, a busy machine, an outdated daemon, a GitHub failure tried again). Help: "Tickets" > "What the Orchestrator deletes after a merge", which also says how to get a deleted branch back with GitHub's **Restore branch**.
- Tickets: **Cancel** now closes the ticket's open pull request on GitHub, just after the cancellation. When GitHub cannot be reached or refuses, the Orchestrator tries again at each GitHub check, and stops if it finds the pull request merged. A ticket reopened after a cancellation keeps its pull request closed until its next accepted submission reopens it. Activity shows "Pull request closed without merging" ("since the ticket was cancelled") and "Pull request not closed".
- Needs you: a pull request closed on GitHub without merging, or merged into another branch than the default one, while its ticket is neither done nor cancelled, is now listed as "Pull request closed without merging for …" or "Pull request merged into … for …", saying when and that the ticket is unchanged. A closed one has **Reopen pull request** (GitHub's reason shown when it refuses, and that the next accepted submission opens a new pull request when its branch is gone) and **Cancel the ticket**; one merged into another branch, which GitHub never reopens, has **Cancel the ticket** and **Mark as done manually**. A pull request the Orchestrator closed at **Cancel** is not listed. Help: "Needs you" > "Closed pull requests".
- Runs: while the ticket's pull request is closed on GitHub, a run waiting for CI is no longer accepted as "No CI found": the run page says the pull request is closed, and the run keeps waiting until you reopen it, or until **CI wait at submission** ends the run (not counted as a failed attempt). Help: "Runs" and "Tickets" > "Waiting for CI".
- Runs: when only another service's statuses passed on GitHub (a deployment preview, a linter app) and no workflow ran, the Orchestrator now asks GitHub whether the pull request conflicts with the default branch before accepting the work: a conflict goes back to the agent as a CI round, and the run waits while GitHub has not said. While the pull request is closed on GitHub, a conflict is not sent to the agent: the run keeps waiting until you reopen it, or until **CI wait at submission**. Help: "Tickets" > "Waiting for CI".
- Tickets: on **Awaiting merge**, the Orchestrator now checks at every GitHub check whether the pull request conflicts with the default branch (Activity: "Pull request in conflict", "Pull request no longer in conflict"), and compares the approved commit with a pull request changed on GitHub after the review. **Request changes** sent while GitHub reports a conflict tells the next run's agent to merge the default branch, whatever your comment says. The "Needs you" item and the ticket page show these in a later step of this version.
- Fixed: a database connection lost while one of its queries was running (for example during a GitHub check) is now logged as "database connection lost", as an idle one already was.
- Needs you: each ticket on **Awaiting merge** is now listed as "Pull request to merge: …", oldest wait first, with the pull request link, Quality's approval and summary (or "Review skipped"), the CI result, a line when the work changed workflow files, "Conflicts with main: GitHub cannot merge it as it is." when GitHub says so, a line when the pull request's head changed on GitHub after the approval (with the commits added since), and a line when GitHub could not be checked for it. Merge it on GitHub: the item disappears and the ticket moves to **Done** at the next GitHub check, without reloading the page. **Request changes** on the item is the ticket page's; on a conflict its comment is already filled in, and the agent is told to merge the base branch whatever the comment says. Its introduction no longer says pull requests to merge come later. Help: "Needs you" > "Pull requests to merge".
- Tickets: the ticket page's **Pull request** section now shows what GitHub said of the pull request since, in the words of "Needs you": closed on GitHub without merging (with when, **Reopen pull request**, and GitHub's reason when it refuses), closed when you cancelled the ticket (and kept closed after **Reopen** until the next accepted submission), **Cancel**'s close not done yet with why, "Conflicts with main" (on **Awaiting merge**, **Request changes** comes filled in, as in "Needs you"), the head moved after Quality's review with the commits added, and GitHub that could not be checked. Help: "Tickets" > "When GitHub changes the pull request".
- Tickets: a pull request merged on GitHub into another branch than the project's default one now says so on the ticket page, in the words of "Needs you" (where it was merged and when, and what you can do), instead of only "Merged".
- Reviews: **Start review** on a pull request closed on GitHub now says to reopen it first, on the ticket page and on "Ready for review".
- Help: "Tickets" > "Cancel a ticket" says that cancelling closes the pull request, and "Runs" > "Where the work is" says how the Orchestrator uses the pull request's latest commit.
- Tickets: **Failed attempts before asking you** now stops a ticket whose failed attempts reach it (2 by default): the failure's comment says so, the ticket shows **Stopped**, **Run now** is refused naming the setting and its value, and Needs you lists it as "Stopped after repeated failures" with **Try again** (no session; the counts start from 0), **Cancel the ticket** and **Mark as done manually**. **Check CI again** that accepts the work after one CI failure too many also lifts the stop. Help: "Runs" > "When a ticket keeps failing".
- Runs: when a machine cannot download the project from GitHub as a run starts (GitHub could not be reached, GitHub refused the token, or the download took longer than **Longest push**), the run now ends with "the project could not be downloaded from GitHub", which no longer counts as a failed attempt. The run page and the ticket's comment say which of the three happened and what to do, naming the token permission to give in the words of GitHub's token page. Needs you shows "… could not be downloaded from GitHub on …" with **Run now**, until a new run starts, the ticket is done or cancelled, or the machine is revoked; a review run that fails this way shows "Review did not finish" with the same words. Help: "Machines" > "When the project cannot be downloaded from GitHub".
- Fixed: Settings > GitHub could show Contents and Pull requests **Missing** for a token made with "Only select repositories", because the check tried writing on another of your public repositories, which the token does not include. The check now tries on a project's repository; with no project yet, such a refusal shows **Could not verify** and says to create a project, then check again.
- Fixed: the run page of a run that ended because its machine could not download the project said the ticket's branch was on the machine "as this run left it", though the run never made one.
