# 04 — Ticket Lifecycle and Definition of Done

> Status: Draft v0.1
> Related: [01 — Domain Model](01-domain-model.md), [05 — Daemon](05-daemon.md), [06 — MCP](06-mcp.md), [07 — Scheduler](07-scheduler.md)

This document defines the ticket states, who may move a ticket between them, and the checks that guard each transition. The rules are enforced by the web application: an MCP call or UI action that breaks them is rejected with an explanation.

## 1. States

| State | Meaning |
|---|---|
| `proposed` | Part of a plan not yet approved, or created by an agent with `ticket.create` and not yet accepted by the owner. Plan tickets are not visible on the board by default; tickets proposed by agents are (02, section 6.3). |
| `todo` | Approved and waiting for work. May be blocked or not assigned yet. |
| `in_progress` | A run is working on it. |
| `waiting_human` | An agent asked the owner a question. Work is paused until it is answered. |
| `in_review` | A pull request is open, CI is green, and the work waits for the Quality agent's review, which the owner starts with **Start review** or skips with **Skip review** until the scheduler starts reviews (lot 4; owner's decision, lot 3 step A). **In lot 2**, before pull requests and Quality exist, it means "work finished, the owner checks it": the agent submitted its report, no Quality run exists, and the ticket waits for the owner to mark it as done manually, send it back with **Request changes**, cancel it, or leave it (owner's decisions, lot 2 steps A and L2). Tickets left in `in_review` by 0.3.0 have no pull request and keep that meaning: **Request changes** and **Mark as done manually** (lot 3 step A). |
| `awaiting_merge` | Review approved, or skipped by the owner. The owner must merge the pull request on GitHub. |
| `done` | Pull request merged, or marked as done manually by the owner. Terminal. |
| `cancelled` | Abandoned. Terminal, except that the owner can reopen it. |

Blocked and eligible are derived conditions of `todo` (see 01, section 3.4). They are shown in the UI but are not states. The UI shows "Blocked" for `proposed` and `todo` tickets only, the states in which dependencies can still change; the API's `blocked` flag is computed for every ticket (owner's decision, lot 1 step F).

```mermaid
stateDiagram-v2
    [*] --> proposed: PM creates in a plan, or agent creates with ticket.create
    [*] --> todo: owner creates
    proposed --> todo: owner approves plan, or accepts an agent's ticket
    proposed --> cancelled: plan rejected or superseded, or owner rejects an agent's ticket
    todo --> in_progress: scheduler or Run now starts a run
    in_progress --> waiting_human: agent asks a question
    waiting_human --> in_progress: owner answers
    in_progress --> in_review: agent submits, DoD passes, CI green
    todo --> in_review: Check CI again finds CI passed after a CI timeout
    in_review --> waiting_human: Quality asks a question
    waiting_human --> in_review: owner answers Quality
    waiting_human --> in_review: owner stops a review run, or its machine is lost
    in_progress --> todo: run fails (retry), or owner stops the run
    waiting_human --> todo: owner stops the run, or its machine is lost
    in_review --> awaiting_merge: Quality approves, or owner skips the review
    in_review --> todo: Quality or owner requests changes
    awaiting_merge --> done: PR merged on GitHub
    in_progress --> done: PR merged on GitHub
    in_review --> done: PR merged on GitHub
    awaiting_merge --> todo: owner requests changes
    todo --> cancelled
    in_progress --> cancelled
    waiting_human --> cancelled
    in_review --> cancelled
    awaiting_merge --> cancelled
    todo --> done: owner marks as done manually
    in_progress --> done: owner marks as done manually
    waiting_human --> done: owner marks as done manually
    in_review --> done: owner marks as done manually
    awaiting_merge --> done: owner marks as done manually
    cancelled --> todo: owner reopens
    done --> [*]
    cancelled --> [*]
```

## 2. Transitions and who may perform them

| From → To | Performed by | Guard |
|---|---|---|
| (new) → `proposed` | Project Manager | Created inside a plan. |
| (new) → `proposed` | Any agent with `ticket.create` permission | Outside a plan. Limited per run (see section 8), flagged "created by agent", listed in "Needs you". The project is `ready` and not archived. |
| (new) → `todo` | Owner | — |
| `proposed` → `todo` | System, when the owner approves the plan | — |
| `proposed` → `todo` | Owner, with **Accept** | The ticket was created by an agent (no plan). |
| `proposed` → `cancelled` | System, when the plan is rejected or superseded | — |
| `proposed` → `cancelled` | Owner, with **Reject** | The ticket was created by an agent (no plan). An optional comment is posted as a `status_change` comment. |
| `todo` → `in_progress` | Scheduler, or the owner with **Run now** | Ticket is eligible (01, section 3.4) and its account can start a run (07, section 2, step 1, without the schedule windows); a run is created. Until the scheduler exists (lot 4), Run now is the only way a run starts (owner's decision, lot 2 step A). |
| `in_progress` → `waiting_human` | Assigned agent, by posting a `question` | Question body is not empty. |
| `in_review` → `waiting_human` | Quality agent, by posting a `question` during a review run | Question body is not empty. The answer returns the ticket to `in_review` in the same run (owner's decision, lot 3 step A). |
| `in_review` (unchanged) | Owner, with **Start review** | The ticket has a pull request, no review run is active, and the pull request's head on GitHub is the commit CI checked for the accepted submission (section 3.2). A `review` run starts with the `quality` profile on any machine; the ticket's status does not change (owner's answers, lot 3 step H). |
| `in_review` or `waiting_human` (a review run's question) → `in_review` | Owner, with **Stop run**; System, when a review run ends without its decision applied | The review run is stopped, fails or ends otherwise (its machine lost included): the ticket stays, or returns to, `in_review`, never `todo`, and the attempt count is unchanged (section 3.2; owner's answer 6c, lot 3 step H). |
| `waiting_human` → `in_progress` (or `in_review` for a review run's question) | System, when the owner posts an `answer` | The waiting run continues: its live session receives the answer, or, after the waiting run lifetime, the same run is resumed on the same machine at once (section 6). |
| `in_progress` or `waiting_human` → `todo` | Owner, with **Stop run** | Not a review run (above). The run is stopped and `cancelled`; the attempt is not counted; the branch is kept; a `status_change` comment records it. The server cancels the run at once, in one transaction with the ticket's status, the comment, the events and the revocation of the run's token (so any later MCP call from that session is refused), then sends `run.stop`; the daemon's later end report only adds the branch and its commits. A session whose end the daemon never reports is stopped by the reconciliation at its next `hello` (05, section 6) (owner's decision, lot 2 step J). |
| `waiting_human` → `todo` | System | Not a review run (above). The waiting run's machine is offline when the answer arrives, or the owner stops a run whose machine is offline: the run fails with `machine_offline`, which is not counted as an attempt. The same applies when the machine does not confirm the answer's `run.resume` within the dispatch acknowledgement timeout, or refuses it: the answer stays in the comments, and the next run's first message holds it (owner's decision, lot 2 step K). Formally the ticket passes through `in_progress` (the answer), then returns to `todo` with the run's end. |
| `proposed` → `todo` or `cancelled` | Owner, with **Accept** or **Reject** (lot 2 step K) | Only a ticket an agent created (`created_by` agent); a ticket the owner created in `proposed` is refused. **Reject** posts its optional comment as a `status_change` comment. |
| `in_progress` → `in_review` | Assigned agent, by calling `ticket.submit` | Submission checks pass and CI passed (section 3.1; the reduced checks of lot 2 until lot 3). |
| `todo` → `in_review` | System, on the owner's **Check CI again** | The ticket's last run ended with `ci_timeout` (without a conflict) or `ci_failed` (on a failure), and CI has passed since for the stored submission, or "No CI found" (section 3.1); no session starts (owner's decision, lot 3 step A; steps G2b and G2c). After `ci_failed`, that run's failed attempt no longer counts (`attempt_count` down by one, never below 0). |
| `in_progress` → `todo` | System | Run failed; retry policy applies (section 5). A dispatch the machine did not acknowledge in time (07, section 8) returns the ticket to `todo` too, without counting an attempt. |
| `in_review` → `awaiting_merge` | Quality agent, by approving | Review checks pass (section 3.2). Applied when the review run ends `submitted` (section 3.2). |
| `in_review` → `awaiting_merge` | Owner, with **Skip review** | No review run active (else refused, `review_active`; lot 3 step H2). A `system` `status_change` comment says "The owner skipped the review."; "Needs you" and the pull request show "review skipped" (owner's decision, lot 3 step A). |
| `in_review` → `todo` | Quality agent, by requesting changes | At least one `review` comment explaining what to change, applied when the review run ends `submitted` (section 3.2). Next run has purpose `fix_review` (from lot 3 step I; until then an `implement` run whose comments hold the points). Never a failed attempt. One request more than **Most review rounds per ticket** stops the ticket instead (section 5). |
| `in_review` → `todo` | Owner, with **Request changes** | From lot 3 (owner's decision, lot 3 step A): offered while no review run is active, never during one (refused from lot 3 step H2, `review_active`); the next run has purpose `fix_review`, with the owner's comment as its point; it is also kept for tickets left in `in_review` by 0.3.0 without a pull request. Lot 4 decides again when reviews start by themselves. Lot 2: a comment explaining what to change is mandatory, posted as a `status_change` comment. `attempt_count` is unchanged (the run succeeded, it is not a failed attempt) and the branch is kept. Nothing starts by itself: the owner starts the next run with **Run now**, which the confirmation offers directly with its usual refusals; it runs on the machine holding the ticket's commits (07, section 3), with purpose `implement`, and its first message holds the comment and says to continue the earlier commits (03, section 3.2). Whether it stays once Quality reviews `in_review` tickets is decided in lot 3 (owner's decision, lot 2 step L2). |
| `awaiting_merge` → `done` | System | GitHub reports the pull request merged into the default branch. A merge found while the ticket is in another state with an open pull request (`todo`, `in_progress`, `waiting_human`, `in_review`) also moves it to `done`, stopping an active run, with a `system` comment saying the pull request was merged before the review finished (owner's decision, lot 3 step A). |
| `awaiting_merge` → `todo` | Owner, with **Request changes** | Owner comment explaining the requested change, posted as a `status_change` comment; the next run has purpose `fix_review`, with the comment as its point. When the pull request conflicts with the base branch, the comment is filled in, asking to merge the base branch and resolve the conflicts (owner's decision, lot 3 step A). |
| any non-terminal → `cancelled` | Owner; Project Manager with owner approval | Active run is stopped; the branch and pull request are closed but kept. A pull request closed without merging on GitHub changes nothing by itself: "Needs you" shows it with **Reopen pull request** and **Cancel ticket**. A ticket reopened after a cancellation keeps its pull request closed until its next accepted submission reopens it (owner's decision, lot 3 step A). |
| `todo`, `in_progress`, `waiting_human`, `in_review` or `awaiting_merge` → `done` | Owner, with **Mark as done manually** | A comment explaining why is mandatory (posted as a `status_change` comment). Active run is stopped; the branch and pull request are left as they are. Tickets it blocked are unblocked. Allowed even while the ticket waits for tickets not `done`; the confirmation then warns and names them (02, section 6.4). |
| `cancelled` → `todo` | Owner, with **Reopen** | None. The ticket keeps its number, history and dependencies; `attempt_count` is reset to 0. |

Every transition writes an event (01, section 3.10) naming who performed it. Tickets are never deleted: a ticket created by mistake is cancelled.

A ticket's fields can be edited only in `proposed` and `todo` (02, section 6.4). The same applies to its dependencies: they can be added or removed only while the waiting ticket is `proposed` or `todo`, whatever the state of the blocking ticket (owner's decision, lot 1 step E).

Agents can never set `done` or `awaiting_merge` on their own work, and the Quality agent can never review a ticket it implemented. Only the owner can mark a ticket as done manually or reopen it.

## 3. Definition of Done

The DoD is checked at two points. The first check is mechanical and done by the system. The second is a judgement made by the Quality agent.

### 3.1 Submission checks (`in_progress` → `in_review`)

When the assigned agent calls `ticket.submit`, it sends a **DoD report**:

- for each acceptance criterion: `met` or `not_met`, with a one-line justification. A criterion is something the agent can show in its own work; CI is the system's check (below), never a criterion, since a criterion such as "CI passes" could not be reported `met` at the first submission (owner's decision, lot 3 step A; Help > Tickets);
- tests added or changed (file paths), or a justification when none are needed;
- documentation updated (file paths), or a justification when not needed;
- ADRs added, if a technical decision was made;
- a short summary of the change for the pull request description.

The system then checks mechanically:

1. every acceptance criterion is reported as `met`;
2. the worktree is clean, and the daemon pushed the branch to GitHub with commits ahead of the default branch (the push result comes with the worktree facts, 05 section 4.9);
3. the rules for the ticket type are satisfied (section 3.3), as a check of the report's form: where the table says "Required", the report lists paths or gives a justification; and every path listed is changed on the branch (the daemon sends the files changed against the base branch);
4. a pull request is open from that branch: the **server** opens it, or updates its description, only when checks 1 to 3 pass, never for a push at a run's end;
5. CI on the pull request has completed and passed.

Checks 1 to 3 answer the call at once: a failure rejects it with the list of failures (`DOD_FAILED`), the agent continues working in the same run, and no pull request is opened or updated. When they pass, the report is stored, the pull request is opened or updated, and the call answers `pending_ci`: the agent ends its turn and the run waits for CI with its session open, counting no working time and no idle time, and still counting against its account's maximum concurrent runs (owner's decisions, lot 3 step A).

**The pull request** (owner's decisions, lot 3 step A): title `<number>: <title>`; a normal pull request, not a draft; its description is filled in from the template `agents/templates/pull-request.md` with the report (summary, criteria as a checklist, tests, documentation, ADRs) and a link to the ticket page. When the branch changes anything under `.github/workflows/`, the description, the review run's first message and "Needs you" say so: an agent could weaken the checks that judge its own work, and a changed workflow runs on GitHub before anyone reads it. The flag is raised when a changed path starts with `.github/workflows/` (case-sensitive), and also when the changed files were cut at their budget (section 8): the safe side (owner's decision, lot 3 step F).

**When it is opened** (owner's decisions, lot 3 step F): an accepted submission never waits for GitHub inside the agent's tool call. One transaction stores the report and each check's result, records the run's decision, marks the ticket "pull request wanted" and writes the event; the agent is answered at once; a background task, one per ticket at a time, then opens or updates the pull request and records its number, link and head. When that fails (GitHub unreachable, a permission missing, an answer that cannot be read, naming its fields), the ticket keeps its state, its page says "Pull request not opened: <reason>" with **Try again**, and "Needs you" lists "Pull request not opened for <ticket>", naming a missing permission in the token page's words ("Pull requests (Read and write)"). It is tried again by **Try again** and once at each server start. Every attempt first looks for the pull request by its branch (`head=<owner>:<branch>`, `state=all`): an open one is updated, a closed one not merged is reopened then updated, and only when there is none is one created; GitHub's "already exists" means looking again. So a server stopped between GitHub's answer and its own record never opens a second one. When several are found, an open one is updated; otherwise only the newest counts: closed without merging it is reopened, merged a new one is opened (GitHub refuses to reopen a merged one); when GitHub refuses a reopen, a new one is opened and the event says so. The ticket wants its pull request until it is opened or updated, or the ticket is done or cancelled (**Request changes** and **Stop run** keep it) (owner's answers, lot 3 step F3). The reasons kept for a failed attempt: GitHub unreachable (no answer, or a server error), no token saved, the saved token unreadable or refused, a permission missing (named "Pull requests (Read and write)" when GitHub names that permission or none), GitHub's rate limit, an answer that cannot be read (its fields named, never a value), and any other refusal in GitHub's masked words, a 404 naming the repository (deleted or renamed, or not visible to the token); a 422 error without a message reads as its field and code (`head invalid`). Each attempt writes `ticket.pull_request_opened` (with the number of a closed one GitHub refused to reopen), `ticket.pull_request_reopened`, `ticket.pull_request_updated` or `ticket.pull_request_not_opened` (lot 3 step F3); repeated failures are quiet: `ticket.pull_request_not_opened` is written when attempts start failing or their reason changes, and the failure keeps the date of the first failed attempt, which "Needs you" and the ticket page show as "Since" (owner's correction, lot 3 step G1a: the CI checks try again every GitHub check interval), the last with the number of the ticket's pull request when it was open (`openPullRequest`: an update failed, "not updated" on the screens; lot 3 step F4).

**Harmless text on GitHub** (owner's decisions, lot 3 step F): the title and every text of the description, the ticket's and the agent's, are masked with the event log's patterns (run tokens `ort_…` included from lot 3 step H3), with local paths made harmless (below), with `<`, `>` and `&` escaped (no HTML; inside code spans and blocks too, where GitHub then shows `&lt;`: owner's answer, lot 3 step F3), and a zero-width space after `@` before a name and after `#` or `GH-` (any case) before digits (also in `owner/repo#12` and in `/issues/12` links, not `/pull/12`), so no mention notifies anyone and no issue reference or closing keyword ("fixes #3") acts at the merge. The description is at most 65,536 characters, its sections cut the longest first with a marker, the link to the ticket always kept; the title at most 256 characters. GitHub documents neither limit nor how it finds mentions and keywords: assumptions A27 and A28 of lot 3's plan, checked by the owner in step N. A closing keyword in an agent's commit message still closes an issue when the commit reaches the default branch: a known limit, said in Help, since neutralising it would mean rewriting the agent's history. **Local paths** (owner's answer 4b, lot 3 step H3) are made harmless only in the texts that leave for GitHub (the pull request's title and description, and Quality's comment review), in one shared place, never in the Orchestrator's own screens, comments or event log: a path inside a run's worktree (`…/.orchestrator/worktrees/<run id>/src/contact.ts`) becomes relative (`src/contact.ts`), and another path in the daemon's folder becomes `~/.orchestrator/…`, whatever comes before that folder (`/home/<user>/`, `C:\Users\<user>\` with either slash, WSL's `/mnt/<drive>/Users/<user>/`, or any other folder). Any other path is left as the agent wrote it. Answer 4b first also turned a home folder (`/home/<user>`, `/Users/<user>`, `/root`, `C:\Users\<user>`, `/mnt/<drive>/Users/<user>`) into `~`; the owner narrowed it on 2026-10-10, before the merge, because those forms are also a web application's page addresses (`/home/dashboard`, `/Users/42`) and the absolute paths a review must quote: "Hardcoded /home/alice/data/file.csv" became "Hardcoded ~/data/file.csv", hiding the very fault reported. The link to the ticket page is `PUBLIC_URL` (09, section 7.1) followed by `/projects/<key>/tickets/<number>`, read at each opening or update; on a loopback address it is followed by "(opens only on the computer running the Orchestrator)".

**Listed paths** (check 3; owner's decisions, lot 3 step F): each path of the report's tests, documentation and ADRs is normalised with POSIX rules (a leading `./` removed, repeated `/` collapsed, a trailing `/` removed, `.` resolved); a path then starting with `/` or `..`, or holding a NUL or a backslash, fails as outside the repository. It must then match exactly (case and bytes) a file the branch changed, as the daemon lists them (05, section 4.9): a deleted file and both paths of a rename count. A folder is not a file: the message asks for file paths and says a folder is not accepted. When the daemon's list was cut at its budget, a path missing from it does not fail: the check reads "could not be fully done", with the number of files changed.

**A push that failed** (check 2; owner's decisions, lot 3 step F): refused for a permission, diverged, or GitHub unreachable, the agent can do nothing about it in its run, which then spends no turns trying: the call is refused with `DOD_FAILED` and a `push` check saying so and telling the agent to end its turn, and the run ends at the turn's end with `push_failed` (section 5), even for a `non-fast-forward` refusal. The agent is told only that check, since it can fix nothing in that run; the other checks are still kept for the owner (lot 3 step F2).

**Each check's result is kept** (lot 3 step F2, owner's addition): `criteria_met`, `worktree_clean`, `commits_ahead`, `pushed`, `type_rules` and `paths_changed`, each `passed`, `failed`, `incomplete` (could not be fully done: the machine's list of changed files was cut, or not sent by a protocol 1 daemon; never a refusal) or `skipped` (no push is tried on a worktree with uncommitted changes or no commits). The accepted submission is kept on the run and, with the report, on the ticket, with the workflow flag (raised too when the list was not sent: the safe side); each run also keeps its latest refused submission, with its report and results, and writes `ticket.submission_refused`. Every text the agent reads comes from the template `agents/templates/submit-checks.md` (03, section 3.2). Each failed or incomplete check also keeps its reasons as facts, one per message (`CheckReason`, lot 3 step F4); the owner's words are made from them by the screens (`apps/web/src/tickets/check-text.ts`), so a later wording fix changes every submission shown, old ones included; a submission kept before F4 has no reasons and shows only its results and the agent's messages. The workflow flag keeps its reason: `changed` when a changed path received starts with `.github/workflows/`, even in the part of a cut list; otherwise `not_listed` when the list was cut or not sent (owner's answer, lot 3 step F4).

**The CI result** is every GitHub Actions workflow run for the pull request's head commit, plus that commit's statuses (02, section 3.1: fine-grained tokens cannot read the Checks API). It has **passed** when all are completed and successful (skipped or neutral count as passed), and **failed** when all are completed and one failed, was cancelled or timed out. The server polls it at the **GitHub check interval** (section 8).

- **No CI found**: when no workflow run or status appears within **Wait for CI to start**, and the pull request does not conflict with its base branch, check 5 reads "No CI found", the submission passes, and the review run is told. When the submission also changed workflow files, the event keeps both facts and the screens say them in one sentence (owner's answer 3, lot 3 step G1).
- **Conflicts with <base branch>** (owner's addition, lot 3 step G1): GitHub starts no `pull_request` run while the pull request conflicts with its base (A18), so before "No CI found" is decided the server reads the pull request's `mergeable` (`null`: read again at the next check, A5). `false` is its own result and the submission never passes: it is sent back to the agent as a CI round, below (owner's answer 1, lot 3 step G2). A conflict appearing after the runs started changes nothing: the submitted commit's result decides.
- **CI failed**: the server sends the agent, with `run.input` (`run.resume` when its session is closed), the template `agents/templates/ci-failed.md` filled in with each failed job and, for each failed step, the step's own part of the job's log, cut to **Longest CI log excerpt** (keeping its end) after reading at most **Longest CI log read** of the log; the agent fixes its work and calls `ticket.submit` again. One failure more than **Most CI failures per run** ends the run as failed with `ci_failed`, a failed attempt.
  A failed step's part of the log runs from its first `##[group]` line at or after its start time to its last `##[error]` line before its end time plus one second, since GitHub gives step times in whole seconds and runs the post steps' clean-up in the same second as the failure (the owner's run of 2026-10-06: the end of a failed job's log is that clean-up, not the failure). Timestamps and colour codes are removed and secrets masked. When the part cannot be cut (no step times, no timestamp, no line or no `##[error]` line within the step's times, or the log larger than **Longest CI log read**), the excerpt is the end of the job's log, and the agent is told it is not the step's part and why. The message keeps its whole text within the `run.input` ceiling by cutting the excerpts further, across all failed steps, the longest first, with a marker.
- **CI rounds** (owner's answers, lot 3 step G2): a failed result or a conflict sent back to the agent is a **CI round**. The conflict's message tells the agent to merge the base branch (`git merge origin/<base>`, never a rebase), and comes with `fetchBase`, so the machine downloads the base branch first (05, section 4.9). A round counts within **Most CI failures per run**, kept on the run at its start (section 8), **once the machine confirmed the message**; one failure or conflict more than that ends the run `ci_failed`, counted, its comment naming the failure or the conflict. The round's message (owner's answer 5): a first round ("CI failed on GitHub for commit …"), a middle one ("CI failed again …", with the rounds left) and the last ("the run ends and counts as a failed attempt" if CI fails again or the pull request conflicts after the next submission); a round that is not the last never says the run ends. Every failure round also says that a failure not coming from the agent's work (GitHub's runner, a secret or a service missing on GitHub) is said with `ticket_give_up`, never handed in again (owner's addition, step G2b). The excerpts are quoted output in fenced blocks longer than any run of backticks inside them, so an excerpt cannot close its block; the whole text stays within `FIRST_MESSAGE_MAX_BYTES`, the excerpts cut the longest first with a marker, the list of failed jobs and steps always complete.
- **One round, delivered once** (owner's point 2, step G2b): a run has at most one unanswered round, kept on the run with a fixed message id, and the server builds no other while it waits. Without an answer after **Machine answer timeout** plus **Longest push** (the base branch's download may take Longest push), the next check sends the same message again, with the same id, and so does the first check after the machine reconnects; the daemon recognises the id and never gives the message twice (05, section 4.4). The first confirmation counts the round, even a late one; in the same transaction the run's wait and its decision are removed, and the agent works on. A refusal is not counted: "session closed" sends the round with `run.resume` at once (as a new message, the first was never given), and any other (the base branch's download failed: GitHub unreachable, **Longest push**, the credential refused, a permission missing) drops the round, keeps the refusal on the run with one `run.ci_round_not_taken` event when it starts or its words change, and the next check decides again. A round never confirmed by **CI wait at submission** ends the run `ci_timeout`, not counted, the detail saying the machine did not confirm it; after a refused conflict, "The pull request conflicts with <base>, and the machine could not download <base> from GitHub: <reason>." While a round is unanswered, GitHub is not read for its run.
- **A new submission** (owner's answer 4, step G2): every outcome is keyed by the commit and applied under the run's lock, so a later result of an earlier commit changes nothing. A submission of a commit a confirmed round of this run sent back (CI failed for it, or its pull request conflicted) is refused with `DOD_FAILED` (check `commits_ahead`, reason `same_commit`), no round counted.
- **Cancelled because the branch moved** (owner's answer 2, step G2): when every failed check is a workflow run GitHub concluded `cancelled` and the pull request's head, read at that result, is another commit (a workflow cancelling its run in progress when the branch is pushed), the run ends at once with `ci_cancelled`, "CI was cancelled on GitHub because the branch changed there", not counted; the next run takes GitHub's branch. While the pull request cannot be read, nothing is decided and the next check reads it again (owner's answer 4, step G2b). A cancellation with the head unchanged is a failure like any other.
- **The deadline** (lot 3 step G2b): a passed result or "No CI found" wins over **CI wait at submission** passed meanwhile; a failure or a conflict found after it ends the run `ci_timeout` instead of a new round, unless it is one too many, which ends it `ci_failed`. The detail says what was found: "CI failed on GitHub (failed: <the failed checks>), and the result was read only after the wait had ended.", or the conflict; the next run's first message then says "CI failed on GitHub for the previous attempt's work, and that attempt ended before it received the result: call ci_status to read it before you start." (owner's review, step G2b), as it says to read the result after `ci_failed` and to merge the base branch after a conflict left unresolved. That run's result still answers `ci_status` (06, section 4.1).
- **CI wait at submission** reached: the run fails with `ci_timeout`, which is not a failed attempt; the ticket returns to `todo` with its branch, pull request and stored report, and "Needs you" shows one of three items (02, section 4; owner's answer 1, lot 3 step G2c): "CI did not finish" with **Check CI again** when CI had not finished or nothing was read; "CI failed for <ticket>, and the agent did not get the result" with **Run now** for a failure read only after the wait or a round the machine did not confirm or refused; "<ticket> conflicts with <base>" with **Run now** for a conflict.
- **Check CI again** (owner's answer 6, lot 3 step G2; answers of steps G2b and G2c) is offered after `ci_timeout` without a conflict and after `ci_failed` on a failure, while no run is active. It starts no session: it reads the timed-out or failed run's commit on GitHub once (the pull request, then the CI result, even a finished one, so it also reads a re-run made by hand on GitHub). "No CI found" counts only once the pull request has been open for **Wait for CI to start** (the run's kept value) since the later of the run's wait start and the pull request's last opening or reopening by the server (kept on the ticket); before that, nothing found is "not finished" (owner's fix, lot 3 step G2c: a pull request opened by **Try again** after the timeout). Passed or "No CI found": the stored submission is accepted, the ticket moves to `in_review` with a `system` comment ("CI passed on GitHub for commit <hash> (checked again by the owner at <time>): the work was accepted without a session."; after `ci_failed`, ", and the failed attempt of that run no longer counts.", `attempt_count` down by one), the item goes. Not finished, failed, a conflict or a GitHub problem: nothing changes, the owner is told why. Refused: a run active, newer accepted work, the branch moved on GitHub, the pull request closed or merged, or no pull request yet ("<ticket> has no pull request on GitHub yet: Try again in "Pull request not opened" opens it."). Each press writes `ticket.ci_checked_again` with its outcome.

**The wait for CI** (owner's answers, lot 3 step G1): the CI result is that of the commit the daemon read with the submission's facts and pushed, kept on the run: the workflow runs of `GET .../actions/runs?head_sha=<hash>` (each run's `head_sha` checked again, another ignored) and the statuses of `GET .../commits/<hash>/status` (GitHub's `sha` must be the hash, else the answer is unreadable), never the branch, the pull request's current head or an earlier submission's commit. The branch moving on GitHub during the wait changes nothing: the result's event says when the pull request's head is another commit. The wait begins at the submission when the ticket's pull request is open (as last seen), whether or not its description update then succeeds, else when the pull request is opened or reopened; **Wait for CI to start** and **CI wait at submission** count from then, and a pull request never opened ends the run `ci_timeout` at the submission plus **CI wait at submission**. The two waits are those resolved when the run started (section 8). The server checks every waiting run one after another at each **GitHub check interval**, a check never overlapping the previous one: 2 requests per run (one more per further 100 runs or statuses), plus one read of the pull request for `mergeable` when nothing appeared after **Wait for CI to start**, and one at a result that decides (the head-moved fact). GitHub unreachable, its request limit (the rest of the check waits for GitHub's reset time) or an answer that cannot be read never end a wait: the run keeps its latest failed check, with one event when checking starts failing or its reason changes and one when it works again; only **CI wait at submission** ends a wait. Everything is stored on the run (01, section 3.7), so after a server restart the first check goes on; a result that decides wins over a deadline passed meanwhile. A daemon reporting its end `submitted` while its run waits accepts nothing: the run keeps waiting with its session gone, and the CI result decides (lot 3 step G1a).

**Lot 2 (reduced submission).** Until pushing, pull requests and CI exist (lot 3), `ticket.submit` takes the same input, but only checks that every acceptance criterion is reported `met`, that the worktree has no uncommitted changes, and that the ticket branch has commits ahead of the base branch. When they pass, the report is stored, the run ends `succeeded` and the ticket moves to `in_review` with the lot 2 meaning (section 1); nothing is pushed. When they fail, the call is rejected with the failures, as above (owner's decision, lot 2 step A).

### 3.2 Review checks (`in_review` → `awaiting_merge`)

The Quality agent reviews the pull request and the DoD report. It verifies that:

- the change does what the acceptance criteria say, and nothing unrelated;
- the tests actually test the change, rather than existing only to satisfy the check;
- justifications for missing tests or documentation are acceptable;
- user documentation describes the change from the user's point of view;
- the code follows the project's CLAUDE.md conventions and existing ADRs.

It either approves, posting a `review` comment summarising the verdict, or requests changes with actionable comments. Both are also posted on the pull request as one GitHub review of the "comment" kind: GitHub refuses an approval or a request for changes on your own pull request, and every pull request is the owner's. When GitHub refuses the post, the decision stands in the Orchestrator, with an event and a note on the ticket page (owner's decision, lot 3 step A). It is posted at most once, after the decision is applied, on the reviewed commit; a lost answer or a server restart is settled by reading the pull request's reviews, never by posting twice (06, section 4.5; lot 3 step H3).

**The commit under review** (owner's answers 2 and 4, lot 3 step H). **Start review** reads the pull request on GitHub (one request): its head must be the commit CI checked for the accepted submission, else it refuses without starting a session ("The pull request's head on GitHub (def5678) is not the commit CI checked (abc1234)", with what to do: **Skip review** and check it yourself, or **Request changes**); GitHub unreachable or another problem refuses it with "try again". That commit goes in `run.start`; the daemon fetches the branch, fails the preparation with `review_branch_moved` (not counted) when GitHub's head is no longer that commit, and detaches the worktree at it. The decision is checked against the pull request's head again within the review tool's call (06, section 4.5), and applied only when the run ends `submitted` with no head moved on the machine. A decision made then thrown away (the head moved on the machine, **Stop run** or the machine lost before the end) is shown in "Review did not finish" and on the run page, saying which decision it was and why it was not applied.

**What the review is told about CI** (owner's answer 4, lot 3 step H), never that CI failed or did not finish for work that was accepted: "CI passed on GitHub for commit abc1234."; after **Check CI again**, "CI passed on GitHub for commit abc1234; the owner had it read again after the agent's run ended, and the work was accepted then."; "No CI ran on GitHub for commit abc1234: nothing appeared within Wait for CI to start after the pull request opened. Nothing on GitHub tested this work."; with workflow files changed too, one sentence: "No CI found for commit abc1234, and this work changed files under .github/workflows/: it may have removed or weakened CI. Read those changes first."

CI already ran, so the Quality agent does not run the test suite again unless the diff or the CI result gives a reason. With "No CI found" (in the run or by **Check CI again**, with or without workflow files changed) it is told instead that nothing on GitHub tested this work, so it runs the project's tests and build itself when the project has any, and says in its decision what it ran (owner's answer 4, lot 3 step H). It never changes the branch: a review run never pushes, and when the branch head moved during the review, the run fails with `review_branch_moved`. It may ask the owner with `ticket.ask` (section 2). A review run that fails, gives up or ends otherwise is never a failed attempt of the ticket: the ticket stays `in_review` and "Needs you" shows "Review did not finish" with **Start review** (owner's decisions, lot 3 step A).

### 3.3 Rules per ticket type

| Type | Tests | User documentation | ADR | Notes |
|---|---|---|---|---|
| `feature` | Required | Required if user-facing | If a technical decision was made | — |
| `bug` | A regression test that fails before the fix is required | Required if behaviour visible to users changed | Rarely | — |
| `chore` | Existing tests must pass | Not required | If a dependency or tool was added or replaced | Refactoring, tooling, dependencies. |
| `docs` | Not required | Is the deliverable | No | May be assigned to the Technical Writer. |
| `spike` | Not required | Not required | Required: the spike's findings are recorded as an ADR or a document | Research only; no production code. |

"Required" can be waived only by a justification in the DoD report, which the Quality agent must accept.

The mechanical form check (section 3.1, check 3; owner's decisions, lot 3 step F): the report's schema already asks, for tests and documentation, for paths or a justification. A `docs` ticket also needs at least one documentation path, and a `spike` at least one ADR path or one documentation path; neither can be waived by a justification. A documentation path is a path the agent lists in the report's documentation field and the branch changed, wherever it is: no rule says where documentation lives (a `README.md` counts).

## 4. Git conventions

- One branch per ticket: `t/<number>-<slug>`, created from the default branch at the first run.
- One Git worktree per run, managed by the daemon.
- One pull request per ticket. Later runs (`fix_review`) push to the same branch.
- Pull request title: `<number>: <title>`. The description is built from the DoD report summary and links back to the ticket.
- After a merge, the server deletes the ticket's branch on GitHub unless another open pull request uses it, and a branch GitHub already deleted counts as deleted; the daemon deletes its local copy (05, section 4.11). After a cancellation nothing is deleted, so **Reopen** finds the work (owner's decision, lot 3 step A).
- The daemon pushes only the ticket's branch, by an explicit refspec, never a tag or another branch, and never forces a push. If the default branch moved, the agent brings it in with `git merge origin/<base>` (the daemon fetches before each run), never with a rebase, so the history Quality reviewed is kept. Unresolvable conflicts are raised as a `question`. When the branch on GitHub contains the machine's branch (for example after GitHub's **Update branch**), the daemon fast-forwards the machine's branch when it prepares a run; a branch that diverged fails the push with a clear reason and a "Needs you" item (owner's decisions, lot 3 step A).
- Merge is done by the owner on GitHub. The web application detects merges by polling GitHub.
- Agent commits are authored as "<profile name> (Orchestrator)" with the owner's GitHub noreply address (`<id>+<login>@users.noreply.github.com`, from the id and login stored with the token, 02 section 3.2), so pushes pass GitHub's "block pushes that expose my email" option and GitHub links the commits to the owner's account. The daemon sets them per worktree.

## 5. Failures and retries

A run fails when it crashes, times out, the machine goes offline, or the agent declares it cannot finish.

- A run stopped because the Claude account reached its usage limit, or because the daemon suspects it did, is **not** a failure. The run goes to `paused_quota` and resumes later (see 07 and 05, section 4.10).
- A run stopped by the owner, a run failed with `machine_offline`, a run failed with `machine_revoked` (its machine was revoked while the run was active), a run failed with `claude_code_unsupported` (its machine's Claude Code was missing or too old at the start, 05 section 4.3; owner's decision, lot 2 step J), a run failed with `machine_problem` (systemd-run refused its process scope, 05 section 2; owner's decision, lot 2 step M2) and a dispatch not acknowledged in time are not failed attempts: the ticket returns to `todo` without changing `attempt_count` (owner's decisions, lot 2 steps A and C).
- Lot 3 adds (owner's decisions, lot 3 step A): `ci_timeout` (section 3.1), `ci_cancelled` (CI cancelled on GitHub because the branch changed there, section 3.1; lot 3 step G2b) and `push_failed` (GitHub refused the push or could not be reached; a "Needs you" GitHub item) are not failed attempts. After `push_failed` (lot 3 step F) the ticket returns to `todo` with a `system` comment, and "Needs you" says what happened: a missing permission in the token page's words, "Contents (Read and write)" or "Workflows (Read and write)" (when the work changes `.github/workflows/`), with the link to the token list; any other refusal with GitHub's words, masked; a branch that diverged on GitHub ("the next run brings its commits in with a merge"); GitHub unreachable. The item goes at the next push done, an end push included, or when the ticket is cancelled or done or its machine revoked; it stays while the next run works (owner's answer 4, lot 3 step F2). The `system` comment says the same, or that the push at the run's end succeeded. **Run now** then starts an `implement` run on the machine holding the commits (07, section 3), whose first message says the work is committed but was not pushed and, for a diverged branch, to run `git merge origin/<ticket branch>` first: it says so whenever the ticket's latest push failed on that machine and none was done since, whatever ended the run (owner's answer 5, lot 3 step F2; a run on another machine, after a revocation, starts from GitHub's branch); neither is any failure of a `review` run (`review_branch_moved` included), whose ticket stays `in_review`. `ci_failed` is a failed attempt. The next run's first message then says, in one sentence, that the previous attempt ended after CI failed and that `ci_status` shows it; after a conflict left unresolved (`ci_failed` on a conflict, or `ci_timeout` with the pull request conflicting, the base branch's download failed included), that the pull request conflicts with the base branch and to merge it first (template `implement`; owner's answer 8 and addition 4, lot 3 step G2b). A `fix_review` run that fails by itself (gives up, times out, `ci_failed`) counts like an `implement` run; Quality asking for changes never counts.
- Otherwise, the ticket returns to `todo`, `attempt_count` is incremented and the failure reason is posted as a `system` comment.
- After **2 failed attempts** (**Failed attempts before asking you**), the ticket stays `todo` and is marked "stopped after N failed attempts": **Run now** refuses it, naming the setting and its value, and "Needs you" lists it ("Tickets stopped after repeated failures") with **Try again** (resets `attempt_count`, with a `status_change` comment), **Cancel** and **Mark as done manually**. The same stop applies when Quality asks for changes once more than **Most review rounds per ticket** (owner's decision, lot 3 step A; the system question of earlier drafts had no run to answer it).

## 6. Questions to the owner

- Agents ask questions with the `ticket.ask` MCP tool. The question is posted as a `question` comment and the ticket moves to `waiting_human`.
- The run stays alive for the waiting run lifetime (a setting, default 30 minutes, section 8) so an answer can resume it without losing context. After that, the tmux session is closed but the run stays `waiting_human`, with its worktree and Claude session id kept on its machine; the answer then resumes **the same run** on that machine at once (`run.resume`, 05 section 3.3), without waiting for the scheduler. If the machine is offline, the run fails with `machine_offline` and the ticket returns to `todo` (owner's decision, lot 2 step A).
- The owner answers the latest question of a `waiting_human` ticket (`POST /api/projects/<key>/tickets/<number>/answer`): the `answer` comment names the question it answers, and the ticket moves back to `in_progress`. A live session receives it with `run.input`; if the daemon refuses it because the session closed meanwhile (05, section 4.4), the server sends `run.resume` instead. A run paused on a usage limit keeps the answer in the comments: **Resume** sends the "please continue" message, which points to `ticket_comments` (lot 2 step K).
- The answer is delivered **at once, whatever the Claude account's state** (owner's decision, lot 2 step K): a session still open already receives it that way, and a waiting run held its session. From then on the run counts against the account again, so the account can be one run above its maximum concurrent runs until a run ends (01, invariant 3); on a limited account, the usage limit is detected as usual and pauses the run.
- If the machine does not confirm the `run.resume` of an answer within the dispatch acknowledgement timeout, or refuses it, the run fails with `machine_offline`, as when the machine is offline: not counted, the ticket back to `todo`, the answer kept in the comments for the next run (owner's decision, lot 2 step K).
- A waiting run does not count as active for the Claude account, so other tickets can run meanwhile.
- The UI shows pending questions prominently. They are the owner's main task list.

## 7. What the owner sees

- A board per project with one column per state (`proposed` hidden by default).
- On each ticket: description, acceptance criteria, assignee, dependencies, DoD report, comments, run history with logs, links to branch and pull request.
- A global "Needs you" view listing plans to approve, questions to answer and pull requests awaiting merge.

Three kinds of values are code constants, not settings: the daemon's reconnection backoff (1 to 60 seconds), because the daemon needs it before it is connected and can read any setting (05, section 3.2); the Claude Code minimum and highest validated versions (05, section 2, declared once in `packages/protocol`), because they describe what the code was validated against, not a choice of the owner (owner's decision, lot 2 step D); and the largest message on the daemon connection (1 MiB, `DAEMON_MESSAGE_MAX_BYTES` in `packages/protocol`), a transport limit both sides must agree on before any setting can be exchanged, not an owner preference: longer reports, such as a batch of log entries, are split below it (owner's decision, review of lot 2 step F). Lot 2 step L adds two more (owner's decisions): the realtime stream's keep-alive (every 20 seconds) and the reconnection delay it gives the browser (3 seconds), because they are transport details, like the daemon's reconnection backoff, not a choice of the owner (02, section 1). The project setup polling interval added in lot 1 (`projectSetupPollSeconds`) is removed in lot 2, when the realtime stream replaces the polling (02, section 1); a stored value is dropped with it.

The idle timeout (05, section 5) is described on the screen as: "A run whose agent shows no activity for this long is stopped. Time waiting for you, for CI or for the quota, and time running a command, does not count." It ends the run without a reminder, since reminders are sent at once when a turn ends (owner's decision, lot 2 step F).

The first login delay is never above the longest login delay: a change or a **Reset to default** that would make it so is refused, naming both settings (the same rule as the quota fallback delays, 07 section 8). Two more pairs follow the same rule with a clear message naming both settings (owner's decision, lot 2 step A): "Machine offline after" is at least twice the heartbeat interval, so one lost heartbeat never marks a machine offline; and the MCP call timeout is below the Claude Code MCP tool timeout, so the daemon always answers Claude Code (with `UNAVAILABLE`) before Claude Code gives up on the call. The daemon waits the MCP call timeout for the server; `mcp.json` receives only the Claude Code MCP tool timeout (owner's decision, lot 2 step G). Both are in the Runs group of Settings > Limits. A third rule adds two settings (owner's decision, lot 3 step D1): the MCP call timeout plus **Longest push** stays strictly below the Claude Code MCP tool timeout, because the push at submission happens inside the agent's `ticket_submit` call, before the daemon waits for the server's answer; a change or a **Reset to default** breaking it is refused with `setting_sum_invalid`, naming the three settings and their values (for example "MCP call timeout (30 seconds) plus Longest push (90 seconds) must be less than Claude Code MCP tool timeout (120 seconds)"). The defaults (30 + 60 < 120) fit. One more rule ties two settings to a constant (owner's decision, review of lot 2 step I): the maximum number of acceptance criteria times the longest acceptance criterion is at most 20,000 characters (`FIRST_MESSAGE_CRITERIA_MAX_CHARACTERS`), so the criteria of any valid ticket fit in the byte budget of a run's first message (`FIRST_MESSAGE_MAX_BYTES`, 03 section 3.2). A change or a **Reset to default** breaking it is refused with a message naming both settings, their values and the budget (for example "Maximum acceptance criteria (40) times Longest acceptance criterion (1,000 characters) is 40,000 characters, above the 20,000 characters a run's first message has room for"). The defaults (20 criteria of 500 characters) fit. Lot 3 step F adds the **budgets of a submission's facts** (owner's decisions), code constants in `packages/protocol` for the same reason as `DAEMON_MESSAGE_MAX_BYTES`: they share out that transport limit, which both sides must know before any setting is exchanged, so that a `ticket_submit` and an end report always fit in one message; they change no behaviour the owner chooses. Each part is measured on its JSON encoding, where a character JSON escapes (`\u0001`) takes six bytes: the DoD report at most 256 KiB (`SUBMISSION_REPORT_MAX_BYTES`; a larger one is refused by the daemon before it pushes, with `VALIDATION_FAILED` giving both sizes); the commits of a branch report at most 500 (`BRANCH_REPORT_MAX_COMMITS`) and 256 KiB (`BRANCH_REPORT_COMMITS_MAX_BYTES`), each subject cut at 1,000 characters with a marker (`COMMIT_SUBJECT_MAX_CHARACTERS`); the changed files at most 256 KiB (`CHANGED_FILES_MAX_BYTES`); a push's message at most 4,000 characters (`PUSH_MESSAGE_MAX_CHARACTERS`, 24,000 bytes at worst), keeping its end; the hashes of `notOnGitHub`, at most 500, about 34 KiB; the rest bounded too: the branch name at most 255 characters (`GIT_BRANCH_NAME_MAX_CHARACTERS`), the run token 200 (`RUN_TOKEN_MAX_CHARACTERS`). A list beyond its budget keeps its newest commits, or its first files in sorted order, and counts them all. A `ticket_submit` is then at most about 830 KiB of the 1 MiB, and an end report, whose detail and restored Git configuration are each cut at 2,000 characters (`END_REPORT_TEXT_MAX_CHARACTERS`), about 340 KiB (tests build the largest of each, `budgets.test.ts`). The fields a 0.3.0 daemon also sends (commit subjects, the commit list, the end detail) are cut when read rather than refused, so its reports are still read; above the limit the server would close the connection. The ranges keep the owner from locking themselves out: a login wait is at most 24 hours, and `orchestrator reset-password` (09, section 7.4) also lifts an active wait. Settings added in lots 0 and 1 are global only (owner's decision, lot 1 step G), and so are those added in lot 2. Lot 2 (version 0.3.0) starts using: max tickets an agent may create per run, the waiting run lifetime, the daemon timeouts of 05 section 5 (maximum run duration, idle timeout, maximum nudges), the dispatch acknowledgement timeout and the quota fallback delay (07, section 8), and every setting added by lot 2 above. Every value is read through the one settings resolver (project override, then global value, then default). A setting used only from a later version is shown with "Used from version ..." and can be set before it has any effect.

Changing a limit applies to future actions only; runs and plans already in progress keep the values they started with, and an open login session keeps its expiry date. Every change of a global value or a project override, and every **Reset to default**, writes an event.
