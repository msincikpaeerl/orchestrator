# Testing

## Levels

| Level | Tool | Location | Runs with | Status |
|---|---|---|---|---|
| Unit | Vitest | next to the code, `*.test.ts` | `pnpm test` | in place |
| Integration | Vitest, real PostgreSQL (`postgres-test` of the dev compose file) | `apps/*/test/`, `packages/*/test/` | `pnpm test` | in place |
| End-to-end | Playwright, in the pinned Playwright Docker image | `apps/web/e2e/*.e2e.ts` | `pnpm test:e2e` | in place |
| Documentation links | remark-validate-links | all `*.md` | `pnpm docs:links` | in place |

Rules (also in CLAUDE.md):

- New behaviour needs tests; a bug fix needs a regression test that fails before the fix.
- Integration tests use the real database, never mocks of it.
- The daemon's tmux and Claude Code layer is tested against a fake `claude` executable; no real Claude Code in CI.
- Never weaken or delete a test to make CI pass.

## Asynchronous effects

After an asynchronous cause (a message sent, a connection terminated, a process started, a file written by another process), wait for its observable effect with a deadline, then assert: `waitFor` from `@orchestrator/daemon/testing`, or a local helper that throws naming what it waited for. Never assume the effect has happened after the cause returns, and never use a fixed sleep instead. Give the test a timeout above its deadlines, so that a failure names the missed deadline. To check that something does *not* happen, first wait for an effect that comes after it would have, as `pool.test.ts` waits for a connection's end before checking that its loss was reported once.

Repeated local runs do not prove there is no race: CI is slower (a run took 352 s where the same tests take a fraction locally). Two tests of lot 2 passed every local run and failed in CI for this reason.

## Integration tests

They need the test PostgreSQL, `postgres-test` in `docker/compose.dev.yml` (`127.0.0.1:5433`), never the development one:

```sh
docker compose -f docker/compose.dev.yml up -d --wait postgres-test
```

It runs with `fsync`, `synchronous_commit` and `full_page_writes` turned off, and keeps its data in memory (`tmpfs`, ADR 0031): every start is a clean server, and stopping or restarting it (`docker compose -f docker/compose.dev.yml restart postgres-test`) deletes everything, which is intended; the template is rebuilt by the next test run. Restart it if tests fail in a way that points at the database itself. Never use these settings elsewhere, and never in `docker/compose.yml`.

A test makes its pools with `createPool` and ends them with `endPool(pool)`, both from `@orchestrator/db`, never `new pg.Pool` and `pool.end()`, before dropping its database: `pool.end()` resolves while connections are still closing, and `DROP DATABASE … WITH (FORCE)` would terminate them, an unhandled 57P01 error in the test process (seen on a slow CI runner in lot 2 steps H and L2). `createPool` follows each connection from its creation to its close, so `endPool` also waits for one that had started closing on its own (released with an error, idle too long), which the pool's own counts had already forgotten.

GitHub is replaced by a local fake (`apps/server/test/fake-github.ts`), described in [The fake GitHub](#the-fake-github) below. The server takes the API address as `githubApiUrl` and the base of clone URLs as `gitBaseUrl` in `buildApp`. `apps/server/test/helpers.ts` starts the application on a new database and captures its logs, so tests can prove that passwords and tokens never reach them.

Daemons are replaced by a scripted client (`apps/server/test/daemon-client.ts`, ADR 0025): it enrolls with `POST /daemon/enroll`, opens the `/daemon` WebSocket with the machine token, sends `hello` (a healthy machine by default, any field changed by the test), heartbeats or any raw text, and records the server's messages and close code. Tests needing it start the application with `listen: true`, which gives its `url`. Offline detection is tested in milliseconds: `daemonSecondMs` makes one second of the heartbeat settings last, for example, 20 ms.

Rules about concurrent requests (ticket numbers, dependency cycles, project keys, the single use of an enrollment code) are tested by sending the requests at the same time with `Promise.all`; the dependency test was checked to fail without the project lock. Ticket states no lot 1 action reaches (`proposed`, `in_progress`, ...) are seeded directly in the database, never through an API.

The runner (lot 2 step F, ADR 0027) is tested with the host's real `tmux` and `git` and a fake `claude` (`apps/daemon/test/fake-claude/`): a TypeScript program, run through a `claude` shell script that `installFakeClaude` writes in the test's `bin` folder, that checks the launch arguments, runs the run's hooks and status line with Claude Code's documented inputs, writes transcript lines, calls MCP tools, reads pasted messages and plays a JSON scenario (`scenario.ts`; `play(scenario, runId?)`, what it did in `log()`). Each test sets `TMUX_TMPDIR` to its own folder, so its `tmux -L orchestrator` server never meets the owner's. `runner-harness.ts` sets up a `RunManager` in the test process with a recorder for a server that answers tool calls as a test says (`answerTools`), and shortens the run limits with `secondMs`; `runner.test.ts`, `permissions-relay.test.ts` (the `PreToolUse` rules through the real hook, the fake's own MCP client against the real SDK relay, the decision tools, the waiting run lifetime, the status line) and `usage-limits.test.ts` (each signal the fake emits) use it; the usage-limit patterns are also checked by the fixtures in `test/fixtures/usage-limit/`, from the documentation until a real limit is captured; `daemon-runs.test.ts` runs the daemon process against a scripted WebSocket server; `workspace.test.ts` fetches from `git http-backend` behind a Basic authentication server (`git-http-server.ts`); `trust.test.ts` races registrations with another process rewriting the file. Test homes are under `/tmp/od-test-*`: a run's socket path must fit the 107 bytes of a Unix socket. A test home's global Git configuration turns off automatic maintenance (`maintenance.auto=false`, `gc.auto=0`): otherwise a test's own `git commit` starts a detached `git maintenance run --auto`, which can outlive the test and write in a repository while the home is removed (`ENOTEMPTY` on a bare clone's `info` folder in CI, lot 3 step D2); `testing.test.ts` checks that a commit starts none. Test files that use a test home without the runner harness also end with `stopHomeProcesses`. A test's run managers are stopped with `shutdown()`, which awaits the work of their runs in flight, before its tmux server and home are removed (the harness's `afterEach` does it for every manager made with `daemon()`): a tick still running would write in a removed folder. After closing tmux, `stopHomeProcesses` (`testing.ts`) kills every process running with the test home's `HOME` (the fake `claude`, its hooks and commands, a spawned daemon) and waits until none is left: closing tmux only sends a hangup, which a process may ignore or outlive for a moment, and one writing while the home is removed fails the test with `ENOTEMPTY`. Vitest fails a run on any unhandled error or rejection (`dangerouslyIgnoreUnhandledErrors: false` in `vitest.config.ts`, the default kept on purpose), even when every test passed.

The real daemon is tested in two ways. In `apps/daemon`, unit tests cover the connection with fake sockets and a fake clock (`connection.test.ts`), and `test/` runs `doctor` and the commands against fake `git`, `tmux`, `claude`, `systemctl` and `loginctl` (small shell scripts). `@orchestrator/daemon/testing` gives a throw-away home folder (`HOME`, `ORCHESTRATOR_HOME` and `XDG_CONFIG_HOME` in a temporary folder, `PATH` holding only the fakes and Node.js), the fakes, and the `orchestrator-daemon` command run from its sources with `tsx`. The certificate checks use a test certificate authority made with `openssl`. In `apps/server/test/daemon.test.ts`, the real daemon runs against the real server: enrollment, connection, reconnection after `restart()` of the test application (same database and port), revocation, an unknown key and a stop by signal. `daemon-package.test.ts` builds the package, has the server serve it, installs it with npm into a temporary prefix (npm's cache and settings in the test folder) and runs it: `--version` prints the build `/version` reports, and the package's name is the one Help > Machines > "Update the daemon" and the "Needs you" item use. `apps/daemon/scripts/bundle.test.ts` proves what the build identifier depends on: the same for a second build, different when the daemon's or the protocol's bundled code or the package's version changes (a source changed as esbuild reads it, by a plugin), the same for a comment, and no absolute path, home folder or host name in the bundle. Test servers serve no daemon package (`NO_DAEMON_PACKAGE` of `helpers.ts`), so whatever `pnpm build` left never changes a test; a test that needs a provided build writes `<package>.build` in its own `daemonPackageDir`. The end-to-end server provides the fixed build `e2e0e2e0e2e0e2e0`, which its scripted daemon says unless a test gives another `daemonBuild`. A daemon started with `spawnDaemon` runs in its own process group and is stopped with `stop(signal)`, which resolves once no process of it is left: tsx starts the daemon in a child process, so a `SIGKILL` sent to tsx alone left the daemon running after its test (found in lot 2 step M, 140 of them; `test/testing.test.ts`). Every test spawning a daemon also ends with `stopHomeProcesses`. A run manager that was shut down refuses new commands ("The daemon is stopping."), so a test body outliving its test, after a timeout for example, cannot start a session once the harness cleaned up (`runner.test.ts`).

The lot 2 acceptance scenario runs end to end in `apps/server/test/acceptance.test.ts` (lot 2 plan, step M): the real server (`startTestApp` with `gitBaseUrl` pointing to a local Git HTTP remote that asks for the fake GitHub's token), the real daemon process from its sources (`enroll`, then `start`), the host's tmux and Git, and the fake `claude`. The owner's side goes through the API. Scenario A: enrolment, **Run now**, the live log, a question answered live, a ticket proposed, a commit, `ticket_submit`, the ticket `in_review` with the branch and commit that `orchestrator-daemon status` shows too. Scenario B: a detected usage limit (the fake's status line window full for 8 seconds, then the documented `StopFailure`), the account limited until the status line's reset, the session closed, **Resume** refused before the reset and accepted after it, the same Claude session resumed. Scenario C: the daemon stopped and started again while the agent's tool call runs (the session lives on and the run finishes through the new daemon; checked to fail when the run's `state.json` is removed), then **Request changes** and **Run now**, whose first message holds the comment and whose branch continues the first run's. The daemon testing helpers it needs are exported by `@orchestrator/daemon` (`./testing/fake-claude`, `./testing/git-http-server`, `./testing/remote`). Every wait is for an effect seen through the API or `status`, with a deadline; after each test the daemons are stopped, the test's tmux server killed, and `stopHomeProcesses` waits until no process of the test home is left before the home is removed.

Each test file calls `createTestDatabase()` from `@orchestrator/db/testing`: it creates a database with a random name on that server, with every migration applied, and `drop()` removes it. The database is a copy of a template, `test_template_<hash of the migration files>`, migrated once and then reused by every run until a migration file changes; the first test process that needs it builds it under an advisory lock, and templates of other migration files are dropped then. Two test runs with different migration files (two checkouts) cannot use the same server at the same time. Tests of the migrations themselves ask for `createTestDatabase({ empty: true })`: `migrateUpTo(pool, tag)` applies the migrations up to one of them only, to write data as an older version did and then check a later migration (`apps/server/test/event-log.test.ts` does it with the events of `every-event.ts`, which writes every event type through the real code, machines with the scripted daemon). Set `TEST_DATABASE_URL` to use another PostgreSQL server (the database part of the URL is replaced).

## The fake GitHub

`apps/server/test/fake-github.ts` (lot 3 step C, ADR 0033) stands for GitHub: the REST API the server uses and Git over HTTP, on the same address and the same repositories. Tests set the valid tokens with their accounts (`fullAccount()`: every permission, the login `octo-owner`, a private `notes` repository), each account's permissions, plan and repositories. Each repository is a bare Git repository on disk, created at its first use in the fake's folder `/tmp/od-test-github-*` (`github.root`) and written with Git plumbing commands that read no user or system Git configuration; `close()` stops every Git process of the fake and removes the folder (`fake-github.test.ts` checks that no process is left in it). A commit made through the REST API is fetched by Git, and a push is seen by the REST API at once. `repositoryHistory` and `repositoryFiles` read a repository's default branch; `requests` and `gitRequests` record what the fake received (never a credential); `override` replaces any REST answer for one request.

**Git over HTTP.** `<github.url>/<owner>/<name>.git` is a clone URL (`gitBaseUrl: github.url`). `git http-backend` serves it behind `createGitHttpHandler` of `@orchestrator/daemon/testing/git-http-server`, after the same token check as the REST API: the token is the Basic password, with any non-empty user name; fetching a private repository needs Contents read, pushing Contents write (otherwise 403, "Write access to repository not granted."), and a proc-receive hook (Node.js) refuses the update of a branch that adds, changes or removes a file under `.github/workflows/` without Workflows write, with GitHub's reason: ``[remote rejected] (refusing to allow a Personal Access Token to create or update workflow `<file>` without `workflow` scope)``. Both texts are GitHub's, from the owner's run of lot 3 step E3. A public repository is fetched without a credential; any other request without a valid token gets 401, which makes Git ask its credential helper.

**REST API**, with each endpoint's permission (403 "Resource not accessible by personal access token" with `X-Accepted-GitHub-Permissions`, alternatives separated by `;`) and 401 "Bad credentials" for a token it does not know:

| Area | Endpoints | Permission |
|---|---|---|
| Account and repositories | `GET /user`, `GET`/`POST /user/repos`, `GET /repos/{o}/{r}` | Administration write to create |
| Files and Git database | `PUT .../contents/{path}`, `GET .../git/ref/heads/{b}`, `PATCH`/`DELETE .../git/refs/heads/{b}` (deleting a missing branch: 422 "Reference does not exist"), `GET`/`POST .../git/commits`, `POST .../git/trees`, `GET .../git/trees/{sha}` (`recursive`) | Contents; Workflows write for `.github/workflows/` |
| Rulesets | `GET`/`POST .../rulesets` | Administration write; paid plan for a private repository |
| Pull requests | `GET`/`POST .../pulls` (`state`, `head`, `base`), `GET`/`PATCH .../pulls/{n}` (title, body, base, state), `GET .../pulls/{n}/merge` | Pull requests; read one with Pull requests or Contents read |
| Reviews | `GET`/`POST .../pulls/{n}/reviews` (APPROVE and REQUEST_CHANGES refused on your own pull request, COMMENT needs a body) | Pull requests |
| Actions | `GET .../actions/runs` (`head_sha`, `branch`, `event`, `status`), `GET .../actions/runs/{id}`, `.../runs/{id}/jobs`, `GET .../actions/jobs/{id}`, `.../jobs/{id}/logs` (302 to the fake's log host, a link valid one minute) | Actions read |
| Commit statuses | `GET .../commits/{ref}/status` (combined), `GET .../commits/{ref}/statuses` | Commit statuses read |

`github.logRequests` records each download from the log host with its `Authorization` header, so a test can check the token never goes there.

A pull request's `mergeable` is `null` at the first read after its head or its base changed, then computed (`git merge-tree`); `mergeable_state` follows (`unknown`, `clean`, `dirty`).

**The shape of each answer comes from GitHub** (ADR 0035, after the owner's first smoke run: version 2026-03-10 removed `merge_commit_sha` from pull requests, the layer required it, and the hand-written fake sent it). The fake writes only the values it models; before an answer leaves it, `shaped` (`apps/server/test/fake-github/documented.ts`) completes the body to the shape of GitHub's OpenAPI description: every required field present, the nullable ones the fake does not model `null`, the optional ones left out. It then refuses a missing field, a wrong type, a `null` GitHub does not allow and a field GitHub does not document: the fake answers HTTP 500 naming them, which fails the test. The shapes are `test/fake-github/documented/github-rest.json`, extracted from the description of the pinned version at a pinned commit of `github/rest-api-description` by `documented/extract.ts` for the endpoints listed in `documented/operations.ts`. A new endpoint answered with a body needs a line there and a new extract: `pnpm --filter server exec tsx test/fake-github/documented/extract.ts` (it downloads about 13 MB; tests never do). `github.override` replaces an answer; `github.alter` changes the answer after the fake has done GitHub's action (a 201 the layer cannot read for a pull request the fake created). A reply with `cut: true` cuts the connection instead of answering (an answer lost on the way back, after GitHub acted when given through `alter`), and `github.setReachable(false)` stops accepting connections on the same address until `setReachable(true)` (a request that never reaches GitHub); lot 3 step H3.

**The layer against the documented answers** (`apps/server/test/github-documented.test.ts`): every reading of `apps/server/src/github/` gets the plainest bodies the description allows, without the fake: required fields only with every nullable one `null` and one item per list, then nullable objects filled and optional fields present. The layer reads only the fields the Orchestrator uses, each as documented; where it checks more on purpose (the `state` of commit statuses and of listed pull requests, typed as plain strings while the documentation's text lists the values), the test says why. A body it cannot read is the refusal `unreadable`, with `fields` naming each field that did not fit and what came instead, as a type, never a value (`merge_commit_sha: expected string, received nothing`), also logged by the client (`log` of `createGitHubClient` and `storedTokenClient`).

**Where each behaviour comes from.** GitHub's REST documentation for the version the server pins (`2026-03-10`, `apps/server/src/github/client.ts`), cited at each behaviour in `apps/server/test/fake-github/`: the endpoints' pages (pull requests, reviews, workflow runs, workflow jobs, commit statuses, Git trees), "Permissions required for fine-grained personal access tokens", "Troubleshooting the REST API" (the refusal and its header), "Authenticating to the REST API" (401), "Managing your personal access tokens" (a token as Git password), "Choosing permissions for a GitHub App" (Contents for Git over HTTP, Workflows for `.github/workflows`), "Events that trigger workflows" (which runs exist), "About status checks" (statuses and conclusions), "Keeping your pull request in sync with the base branch" (**Update branch**) and "Approving a pull request with required reviews" (no approval of your own pull request). What the documentation does not say (refusal texts, the log format, a few 422 answers) is the fake's guess, listed with how the owner's smoke script checks it in [lot 3 plan](lot-3-plan.md), step E, "Assumptions to confirm on the real GitHub". When the real GitHub answers differently, the fake changes with a test.

**Scripting CI.** A repository lists its workflows: `workflows: [skeletonWorkflow()]` is the skeleton's CI (`pull_request`, and `push` to the default branch; jobs `docs-links` and `ci`); without workflows no run ever exists ("No CI found"). Runs start as on GitHub: a `pull_request` workflow when a pull request is opened, reopened or its head branch moves (by a push, a REST write or **Update branch**), never while it has a conflict; a `push` workflow when a listed branch moves. The repository's `ci` says what a new run does: `queued` (the default) waits for the test, `success` completes it at once, `{ failures: [{ job, step, log }] }` completes it with those steps failing (their log printed, later steps skipped), `none` starts nothing (Actions never starts). As on GitHub (the owner's run of 2026-10-06), after a failure the post steps still run (`Post Run <action>`, skipped when the job lists it in `postIfSuccess`, as `actions/setup-node`'s `post-if: success()`) and `Complete job` succeeds; steps get whole-second `started_at` and `completed_at`; the log has GitHub's format, measured on a real log: every line stamped with seven decimals, a step's section opening with `##[group]Run <action or command>` (a named `run:` step shows its command, from the job's `commands`), the failure ending with `##[error]Process completed with exit code 1.`, the post steps' clean-up in the same second, the log ending with `Cleaning up orphan processes`.

**A real job log** (`apps/server/test/fixtures/github-job-log/docs-links.txt`): the skeleton's `docs-links` job failing on a broken link, from the owner's run, rebuilt from a paste and made anonymous (its README says what was changed: the escape characters put back, no byte order mark, the account replaced). `apps/server/src/github/job-log.test.ts` cuts the failed step's part from it, with and without a byte order mark and colour codes, in chunks of any size, and each fallback with its reason. `readFailedStepLogs` (`apps/server/src/github/ci.ts`) streams the log into `JobLogReader`, reading at most **Longest CI log read**; `github-layer.test.ts` tests that ceiling at the byte. A test moves queued runs with `github.runs(repo, ref)`, `github.startRun(run)`, `github.completeRun(run, failures)` and `github.cancelRun(run)` (conclusion `cancelled`, as a workflow whose `concurrency` cancels the run in progress when the branch moves; a per-test control, the fake's workflows declare no concurrency), and sets commit statuses with `github.setStatus(repo, ref, { context, state })`.

**The owner's actions on GitHub.** `github.commit(repo, branch, files, message, from?)` (someone else's commit, for example on the base branch to make a conflict; a file set to `null` is removed; a missing branch starts from the branch `from`, or with no parent), `mergePullRequest(repo, n, 'merge' | 'squash')`, `closePullRequest(repo, n)` and `updatePullRequestBranch(repo, n)` (merges the base into the head). Each throws when GitHub would not offer it (a merge or **Update branch** with conflicts, a closed pull request). **Update branch** is also served through the API (`PUT .../update-branch`, 202, or 422 when not behind, in conflict or with another `expected_head_sha`; step E3). `github.repository(owner, name)`, `branches(repo)` and `pullRequest(repo, n)` read the state.

**From the end-to-end server.** The control address offers the same functions on the full account's repositories (`apps/server/test/fake-github-controls.ts`): `POST /github/commit` (`from` starts a missing branch from another), `/github/ci` (`action` `start` or `complete`, with `failures`), `/github/status`, `/github/merge`, `/github/close` and `/github/update-branch`, described in `e2e-server.ts`; a refusal answers 409 with the reason.

**No test reaches the real GitHub** (working rule 9, `apps/daemon/test/real-github-guard.ts`). The root `vitest.setup.ts`, loaded before every test file of every package, makes `fetch` refuse github.com, its subdomains and githubusercontent.com, and fails the test after it with "This test tried to reach the real GitHub (working rule 9): GET https://api.github.com/user …", even when the code under test caught the refusal (the server reports GitHub unreachable). Every test home's Git configuration (`$XDG_CONFIG_HOME/git/config`, written by `createTestHome`) rewrites github.com URLs to `http://127.0.0.1:9/a-test-tried-to-reach-github.com/`, so a clone, fetch or push fails with "Failed to connect to 127.0.0.1 port 9" and names why. The daemon's own fetches and pushes read no Git configuration of the test home, by design (05, section 7.1), so every test home also sets `REAL_GITHUB_PROXY_ENV`: `http_proxy`, `https_proxy` and `all_proxy` at the closed port 9, with `no_proxy` for the loopback addresses only; such a fetch fails with "Failed to connect to github.com port 443 via 127.0.0.1" or, with an older curl (the CI runner's), "Failed to connect to 127.0.0.1 port 9". The end-to-end server installs the same `fetch` guard. `real-github-guard.test.ts` and `fake-github.test.ts` check both, including a server started without `githubApiUrl`. The tests' tokens are made up, so even a request that escaped would be refused by GitHub.

## The daemon's fetch and push

`apps/daemon/test/credential-leaks.test.ts` (lot 3 step D1, 05 section 7.1) plants each way to leak the token in the bare clone, the test home's global configuration, `~/.netrc` or `~/.git-credentials`, then pushes, downloads the base branch as before a conflict's message (lot 3 step G2a) and fetches through the daemon with a Git HTTP server delaying each request, and checks five things: a listener on `127.0.0.2` receives nothing; the planted programs (shell scripts that record that they ran and try the daemon's credential socket with what they inherited) never run; the server sees only the run's repository; no file under the test home holds the token; `/proc`, sampled while the commands run, shows the token in no process's arguments or environment, and did see a Git process holding the credential's variables. That file removes the proxy variables of the test home, since `no_proxy` would keep curl from using a planted proxy and hide the attack; it reaches only local addresses. Its "lot 2's fetch" tests were checked to fail with the daemon of `main` before step D1 (the proxy received the token; the planted askpass got it from the socket). `push.test.ts` covers the push (the hash given, never forced, the Orchestrator's refusal, **Longest push** with no process left) and the fetch: a Git wrapper sets `GIT_TRACE2_EVENT`, `GIT_TRACE2_CONFIG_PARAMS` (a canary key planted in the bare clone) and `GIT_TRACE2_ENV_VARS` (the credential socket's variable), and the test fails when one Git process shows both (checked to fail without `core.alternateRefsCommand`); a fetch after one new commit adds a pack of at most 4 objects. `submission-push.test.ts` pushes at `ticket_submit` with the fake `claude`: only the ticket branch, even with `push.followTags=true` and an annotated tag, and the head read for the facts even when a Git wrapper moves the branch just before the push.

`apps/daemon/test/changed-files.test.ts` (lot 3 step F1, 05 section 4.9) reads the facts of a `ticket_submit` with the real Git: the files a branch changed (added, changed, deleted, both paths of a rename, the base merged twice and moved again, no base fetched), the changed files and the commits at their budget and one above, and no program planted in the bare clone's or the worktree's configuration (external diff, text conversion, pager, hooks, file system monitor, `log.showSignature` with a fake `gpg`, a filter) starting. The budgets themselves, and the largest `ticket_submit` and end report within `DAEMON_MESSAGE_MAX_BYTES`, are tested in `packages/protocol/src/daemon/budgets.test.ts`; a failed push ending the run with `push_failed`, and a report above its budget refused before the push, in `submission-push.test.ts`.

Lot 3 step D2 adds, with the same harness: `run-end.test.ts`, the end push on each way a run ends with commits not on GitHub (Claude Code exiting, a give-up, the idle timeout, Longest run, reminders used up, **Stop run**, a cancelled ticket), each waiting for the branch on the Git HTTP server; a refused push leaving the outcome unchanged; and a push held by the server (`startGitHttpServer`'s `delayPushMs` delays push requests only, and `requests` says which were pushes) during which the session, the run's processes and the worktree are already gone, stopped at Longest push. `review-run.test.ts`: a review run's worktree at GitHub's head with a local branch ahead, no push request, a head moved in the worktree or on the local branch. `preparation.test.ts` (Workspaces alone, a `file://` remote): the fast-forward after **Update branch**, a diverged branch kept and reported by `endPush`, a branch a waiting run holds never moved. `git-config-restore.test.ts`: an agent's changes to the bare clone's configuration and hooks left in place, with no event, while a waiting run of the same repository has its worktree, then put back and named when that run, the last one, ends, having committed with its author; `src/bare-config.test.ts` the edge cases (format settings kept, a credential in a setting's name masked, an unreadable file, a `hooks` link). The Git HTTP test server answers 404 "Repository not found." for a repository it does not have, as GitHub does (A24). On the server, `runs.test.ts` covers the ending window of the push credential and the `run.git_config_restored` event.

## systemd tests

`apps/daemon/test/systemd.test.ts` checks the scopes of lot 2 step K with the host's **real** systemd user session, which CI's runner does not have. It runs only when `ORCHESTRATOR_TEST_SYSTEMD=1` is set; it fails (rather than skip) when that is set and a throw-away scope cannot be created (`UserSystemd.detect`, the daemon's own check at start), with systemd's reason. On WSL with systemd:

```sh
ORCHESTRATOR_TEST_SYSTEMD=1 pnpm exec vitest run --project apps/daemon test/systemd.test.ts
```

What it creates, all transient units of the user's systemd (nothing is written in the home folder, and no unit file is installed):

- `od-test-check-orchestrator-scope-check-<random>.scope` and `od-test-<hash>-orchestrator-scope-check-<random>.scope`: the throw-away scopes of the check at start (of the test, then of the daemon), running `true` and gone at once;
- `od-test-<hash>-orchestrator-tmux.scope`: the test's tmux server, started by the daemon code as for the real service;
- `od-test-<hash>-orch-run-<run id>.scope`: each run's fake `claude`;
- `od-test-<hash>-daemon.service`: the daemon started with `systemd-run --user` and `start --service`, whose "Process scopes" check must be ok, stopped and started again to play a restart of the service (a transient service is killed by cgroup like the installed unit).

`<hash>` comes from the test's throw-away `ORCHESTRATOR_HOME` (`unitPrefix` in `apps/daemon/src/systemd.ts`): only the folder `.orchestrator` in the home folder of the user's account (the passwd entry, not `HOME`, which the test's service has in its test home) gets the real names, so a real `orchestrator-tmux` scope or `orchestrator-daemon` service is never named, stopped or touched. The restart test checks that its service's run and tmux server are in `od-test-` scopes (`apps/daemon/src/unit-prefix.test.ts` checks the prefix without systemd). Afterwards, the user journal names no unit without the prefix: `journalctl --user --since "<start time>" --no-pager | grep -E 'Started (orchestrator-|orch-run-)'` prints nothing. Every `od-test-*` unit is stopped (and its failed state reset) after each test and before the first one, so an interrupted run's leftovers go at the next run. To remove them by hand: `systemctl --user list-units --all 'od-test-*'`, then `systemctl --user stop <units>`.

Without a systemd user session, `apps/daemon/test/process-scopes.test.ts` covers the same decisions with fake `systemd-run` and `systemctl` in the test home's `bin` (lot 2 step M2): the service whose scopes are refused reports the "Process scopes" error, refuses `run.start` and starts nothing; a daemon in a terminal keeps the fallback; a run's or the tmux server's scope refused later fails the run with `process_scope_failed`, sends `machine.doctor` and blocks the next `run.start` and `run.resume`; a launch interrupted by **Stop run**, a killed tmux session or a daemon stop never blocks the machine (the fake `systemd-run` can start a run's scope two seconds late). `apps/server/test/daemon.test.ts` checks the item in "Needs you" with the real server.

The `failNextGitHubRequest` fixture uses the same control address to make the next GitHub request with a given method and path ending fail (for example a 503 on `POST .../git/trees` for a failed setup); this control exists only in the test server, never in the Orchestrator. For machines, `connectDaemon` makes the test server enroll the scripted daemon of `apps/server/test/daemon-client.ts` with the code shown on the screen, connect it and say `hello` (with fields to change, such as an old Claude Code), sending heartbeats until the next reset; `comeBack` tells the page it is visible again, as when the owner returns from the terminal, so the screens read their data again. The scripted daemon acknowledges the server's commands by itself, as a real daemon does; runs are played with the controls `POST /daemon/run` (waits for a run's `run.start` or `run.resume`, answering its run token) and `POST /daemon/request` (sends a report or a tool call and answers the server's reply), through the fixtures `runNow`, `startRun`, `reportState`, `sendLog`, `callTool` and `daemonRequest`; `readyForRuns` prepares a ready project, a connected machine and an assigned ticket. A test of a live screen first waits until the page shows its data, then makes the change from outside the page, so only the realtime stream can bring it (`runs.e2e.ts` was checked to fail with the stream turned off). Tests run one at a time.

**Screenshots for the owner** (lot 3 step F4). The owner judges screens from pictures without building the server, so some tests save them with `screenshot(page or part, testInfo, name)` of `fixtures.ts`: `apps/web/e2e-screenshots/<name>.<desktop|phone>.png`, the whole page or one part of it. The folder is ignored by Git and emptied at the start of every run by Playwright's global setup (`e2e/screenshots-setup.ts`), so no picture of an older run stays; the image runs as your user, so the files are yours. CI writes them and throws them away. `submission.e2e.ts` saves `ticket-pull-request-checks-passed`, `ticket-check-not-fully-done`, `ticket-workflow-flag`, `ticket-pull-request-not-opened`, `ticket-pull-request-not-updated`, `run-refused-submission` and `run-refused-then-accepted`.

### Run them on the host

Only when Chromium's system libraries are installed (`apps/web/node_modules/.bin/playwright install-deps --dry-run chromium` lists the missing ones; installing them needs root, which is the owner's decision). Then `pnpm test:e2e:host` downloads Chromium into `.playwright-browsers/` at the repository root (ignored by Git), never into the home folder, and runs the tests.

### Upgrading Playwright

Change `@playwright/test` in `apps/web/package.json` and the image tag in `tools/e2e-docker.sh` and `.github/workflows/ci.yml` together; `apps/web/e2e/image-version.test.ts` fails otherwise.

## Continuous integration

`.github/workflows/ci.yml` runs on pull requests and pushes to `main` (ADRs 0030 and 0032). `pnpm verify` is split into parallel jobs, which together run each of its scripts (a test checks it); each installs the dependencies with `pnpm install --frozen-lockfile` (pnpm store cached) and has a 15-minute timeout:

- Job `checks`: `pnpm lint` (lint, format check, `bash -n` of the scripts in `tools/smoke/` and `tools/spike/`), `pnpm typecheck`, `pnpm docs:links` and `pnpm audit --audit-level critical`.
- Job `test`, in three shards (a matrix, `test (1)` to `test (3)` on GitHub): each starts `postgres-test` from `docker/compose.dev.yml`, as developers do (its log shows `fsync`, `synchronous_commit` and `full_page_writes` off and its data on `tmpfs`), installs tmux from apt and runs `pnpm test --shard=i/3`, a third of the test files. `fail-fast` is off, so every shard reports its failures; `pnpm exec vitest run --shard=i/3` runs the same files locally.
- Job `build`: `pnpm build`.
- Job `e2e`, in the Playwright image with a PostgreSQL service: installs dependencies with the image's Node.js and pnpm (Corepack, pnpm store cached), builds the UI and runs `playwright test`. The report and traces of failed tests are kept as the `playwright-report` artifact for 7 days.
- Job `docker`: builds the image, starts `docker/compose.yml` with a generated `.env`, and checks `/health`, `/version` and that a screen address returns the UI.
- Job `ci`: needs every other job (the shards through the one job `test`) and fails when any of them failed, was cancelled or was skipped. Branch protection of `main` requires only this check, so jobs can be added or renamed without changing it; list every new job in its `needs` (a test checks it) and never rename or remove `ci`.

To check the workflow file locally:

```sh
docker run --rm -v "$PWD:/repo" -w /repo rhysd/actionlint:1.7.12
```

CI must stay under 10 minutes (08, section 4): the timeouts are a safety net, not a target. When a job grows too long, split it further (for example test shards) rather than raising its timeout.

Vitest gives each shard the same number of test files, ordered by a hash of their paths, not by duration, so the slowest files (the daemon's runner tests, `acceptance.test.ts`, `tickets.test.ts`) decide the balance; on 2026-10-02 the three shards held 24 %, 42 % and 35 % of the test file time (ADR 0032). When a shard takes more than 8 minutes, add a shard: append the next number to `shard: [1, 2, 3]` in the `test` job, nothing else changes (tests check that the shards are numbered 1 to their count and that `ci` needs every job).
